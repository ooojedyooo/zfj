# 炸飞机 · zfj

微信**小游戏** · 双人实时对战。

在 9×9 棋盘上布置飞机，双方轮流报点轰炸，**击毁对方全部飞机者获胜**。
规则源自纸笔时代的经典对战游戏，数字化后支持在线房间、按架数快速匹配、按房名搜索与好友邀战。

---

## ⚠️ 先读：这是「小游戏」，不是「小程序」

微信把两者按**注册时的服务类目**区分，**且注册后不可逆**：

| | 微信小程序 | 微信小游戏 |
|---|---|---|
| 入口文件 | `app.json` + `app.js` | `game.json` + `game.js` |
| 界面 | WXML + WXSS，多页面路由 | **没有 WXML/WXSS/DOM，全靠 Canvas 手绘** |
| 本项目 | `miniprogram/`（保留作参考实现） | **`minigame/`（当前主线，用于上架）** |

本账号的服务类目是**游戏**，即小游戏账号 —— 用小程序工程去编译会直接报
`miniprogram/game.json: 未找到 或者文件读取失败`（工具按 **AppID 的账号类型**决定编译模式，
`project.config.json` 里的 `compileType` 改不动它）。

因此实际交付**重构为小游戏 Canvas 版**。好消息是：`config/`（规则 / 机型 / 道具 / 社交）、
`utils/`（形状 / 旋转 / 碰撞 / 判定）、`services/`（统一数据接口 / 离线引擎 / 最近对手）、
`cloudfunctions/`（云函数）**全部原样复用**——它们不依赖 WXML。只有渲染与交互层重写了。

## 两套端的关系

```
                         ┌──────────────────────────────────────────┐
                         │  共享真源 miniprogram/{config,utils,services} │
                         └──────────────────────────────────────────┘
                                   │ scripts/sync-shared.js 单向同步
        ┌──────────────────────────┼──────────────────────────┐
        ▼                          ▼                          ▼
cloudfunctions/*/shared/    minigame/js/shared/       （小程序自身的 config/utils/services）
  仅供云函数使用             小游戏端使用的副本
        │                          │
        ▼                          ▼
   云端权威判定            minigame/js/{core,widgets,scenes}  ← 只有这层是新的
```

- **逻辑唯一真源**：玩法逻辑只写一遍，小游戏端与云函数拿的都是同步出来的副本
- **改完 `miniprogram/{config,utils,services}` 必须重跑 `node scripts/sync-shared.js`**，
  并**重新上传 `room` / `game` 云函数**，否则两端逻辑会漂移
- `miniprogram/` 里**只有 `config` / `utils` / `services` 是真源**，`pages` / `components`
  那套 WXML 界面层**已冻结**（2026-10-29 决定：不再补新功能、不再跟规则改动同步）。
  冻结不影响任何构建产物——`sync-shared` 本来就只扫那三个目录

## 玩法规则

| 规则项 | 说明 |
|---|---|
| 棋盘 | 9 × 9，坐标「横X竖Y」，左上角为原点 |
| 飞机 | 每架 **10 格** = 机头 1 + 机翼 5 + 机身 1 + 机尾 3 |
| 数量 | **房主开房时定死 1~3 架**，双方相同；布阵必须摆满，多一架少一架都不许开局 |
| 方向 | 支持 4 向旋转，飞机之间不可重叠、不可出界 |
| 回合 | **严格交替**：无论是否命中，开一炮就换手 |
| 每步限时 | 房主建房时用**滑块**设定，**5~30 秒、1 秒连续**，开局后双方一致 |
| 超时 | 系统替该玩家**从上到下、从左到右**打第一格没炸过的位置；**连续超时 5 次判负** |
| 判定 | 击中机头 = 整机立即击毁；击中其余部位 = 击中；空白 = 未击中 |
| 关键规则 | 飞机被击毁后**不揭示形状与朝向**，需玩家自行推理 |
| 胜负 | 先击毁对方全部飞机者获胜 |

> ✅ **T-11 已定案**：架数由**房主开房时定死**（1 / 2 / 3 架），房间上写着它，
> 列表里也显示它；布阵时**必须摆满同样多才能开局**。
>
> 曾经试过「架数由各自在布阵页决定」，但那样「少放一架」在数学上占优 ——
> 对方要击毁的目标更少、你的机位暴露也更少，于是存在「双方都只放 1 架」的退化策略，
> 把对局变成纯抽奖。传统海战棋的解法正是**舰队编制公开且双方相同**，这里回到那条路上。
>
> 「随机匹配」也因此拆成**三个选项**（1 / 2 / 3 架）：想打多大的局，在点下去之前就得说清楚，
> 因为进去之后已经改不了了。

## 技术设计要点

### 1. 数据驱动（可扩展性的关键）

机型与道具均以**配置**描述，而非写死在逻辑里：

```js
// config/planes.js —— 新增机型只需追加一条记录
{
  id: 'standard',
  name: '标准机',
  cellCount: 10,
  headIndex: 0,          // 机头在 cells 中的下标
  cells: [ [0,2], [1,0], ... ]   // 相对坐标 [row, col]
}
```

- 摆放校验、命中判定、棋盘渲染全部复用同一套逻辑
- 新增机型 / 新增道具（如「超级导弹」）**无需改动核心代码**

### 2. 逻辑与界面分离

`utils/` 下全部为纯函数，不依赖任何宿主 API（小程序也好、小游戏也好），可用 Node 直接运行测试。

这是能从小程序平滑迁到小游戏的根本原因 —— **玩法的正确性从不由 UI 承担**。

### 3. 小游戏端为什么需要自研一层「UI 框架」

小游戏没有 WXML/WXSS，没有 `<view>`/`<button>`，只有一块 canvas。所以 `minigame/js/core/`
里补了一套最小可用的替代品，思路是把「页面开发习惯」重新做出来：

| 小程序里的东西 | 小游戏端的对应实现 |
|---|---|
| `App.globalData` | `app.globalData` |
| `wx.navigateTo` / `redirectTo` / `navigateBack` | `app.go` / `app.replace` / `app.back`（自己维护场景栈） |
| `Page({ data, setData })` | `Scene` 子类：属性直接赋值 + `layout()` 重算 zones |
| WXML 布局 | `layout()` 里算好每个区域的 `{x,y,w,h}`，元素各画各的 |
| `bindtap` | `this.zone(x, y, w, h, onTap)` 注册命中区，`app` 统一分发 |
| `wx.showModal` | `core/dialog.js` 封装（小游戏没有表单控件，用 `editable` 弹窗代替） |
| WXSS 里的颜色字号 | `core/theme.js`（与小程序 `app.wxss` 同源常量） |

触摸分发上做了两个小细节：**后注册的 zone 优先命中**（浮层盖住底层时天然正确），
以及**拖动超过 10px 就不算点击**（避免滑动误触发）。

### 4. 关键规则在代码中的落地

| 规则 | 落地位置 |
|---|---|
| 击毁不揭示形状（T-08） | `judge.js` 只返回命中结果，绝不下发飞机完整格位；**架构级保障**：飞机布阵存在权限为「所有用户不可读写」的 `games` 集合，客户端根本读不到 |
| 已攻击格不可重复选中（T-04） | 两端都在界面层根治：小程序是 `board-grid` 组件的 `disabledMap` 置灰，小游戏是 `widgets/board.js` 的 `selectable` + `disabled` 标记；服务端二次校验兜底 |
| 严格交替 | `localGame.js` 中 `fire()` 后立即换手，云端 `game.fire` 同步换手 |
| 布阵超时兜底（T-03） | `plane.js` 的 `randomDeploy()` |
| 表情内容安全 | `config/social.js` 白名单，客户端渲染与云端校验**同源**（`sync-shared.js` 保证） |
| 双棋盘不出屏 | 小游戏端 `scenes/battle.js` 按屏高动态分配上下两块棋盘尺寸，`test-minigame.js` 有断言 |

### 5. 一套接口，两种数据源

场景 / 页面只 `require('shared/services/cloudApi')`，拿到的方法在任何模式下都一样：

```
             ┌─ USE_CLOUD = true  → shared/services/cloudImpl.js    （云函数 + 云数据库 watch）
cloudApi.js ─┤
             └─ USE_CLOUD = false → shared/services/offlineGame.js （本地对手 AI + 本地事件广播）
```

好处：

- **云环境没配好也能把游戏完整玩一遍**，验证玩法与交互
- 切换数据源只改 `config/cloud.js` 一个开关，场景 / 页面代码零改动
- 离线引擎也是纯逻辑，可用 Node 跑全流程集成测试（见 `scripts/test-offline-flow.js`）
- 同一套接口也是小游戏端能复用小程序端全部数据层的原因

## 本地运行

### 方式一：离线试玩（当前默认，免配置）

`miniprogram/config/cloud.js`（小游戏端读的是同步出来的 `minigame/js/shared/config/cloud.js`）
里 `USE_CLOUD: false`，用**微信开发者工具**导入本目录即可：

```
创建房间 → 约 2.5 秒后「对手」自动加入 → 布阵 → 随机先手 → 轮流开火 → 结算
```

对手由 `services/offlineGame.js` 驱动的本地 AI 扮演（会优先追打已命中格的相邻格），
除对手是 AI 外，其余流程、界面与真实联机完全一致。

> ⚠️ **`project.config.json` 里的 `appid` 必须是本账号的小游戏 AppID**。
> 若填 `touristappid`（游客模式），工具无法判定账号类型，小游戏工程可能编译不起来。
> 反过来，如果把这个 **小游戏 AppID 填进小程序工程**，就会报
> 「`miniprogram/game.json` 未找到」——因为工具是按账号类型决定编译模式的。
> 改完 `appid` 后**需移除项目再重新导入**才生效。

### 方式二：接入云开发（真实双人对战）

1. 把 `miniprogram/config/cloud.js` 的 `USE_CLOUD` 改成 `true`，然后 **`node scripts/sync-shared.js`**
2. 开通云开发并创建环境，把环境 ID 填进 `miniprogram/config/cloud.js`（同样要重跑同步脚本）
3. 在云开发控制台创建 `rooms`、`games` 两个集合并设置权限（见部署文档）
4. 上传 `cloudfunctions/` 下的 `room`、`game`、`cleanup` 三个云函数
5. 编译后即可与另一台设备真实对战

> 完整步骤见 **[docs/云开发部署说明.md](docs/云开发部署说明.md)**

### 运行自测

```bash
node scripts/test-core.js          # 22 项：形状 / 旋转 / 碰撞 / 判定 / 胜负 / 随机布阵
node scripts/test-offline-flow.js  # 45 项：建房 → 布阵 → 开局 → 开火 → 结算 全链路
node scripts/test-minigame.js      # 172 项：小游戏端渲染 + 触摸/拖拽 + 宽松布阵与就绪校验 +
                                   #        大厅三张匹配卡 + 房间页架数与滑块 + 房间列表/搜索 +
                                   #        超时自动轰炸与连超判负（桩 canvas/wx 跑真流程）
node scripts/test-layout.js        # 6 种屏幕尺寸：不出屏 / 不重叠 / 格子 ≥ 30px
node scripts/sync-shared.js        # 改完 miniprogram/{config,utils,services} 后必须重跑
```

`test-minigame.js` 值得单独说一句：小游戏没有 DOM、没有 WXML，通常被认为「没法自动化测」。
但它整个界面层就是「纯计算 + Canvas 调用」，所以只要：

- 用桩 `canvas.getContext('2d')` 顶掉绘制（记录调用序列，可断言「这一帧到底画了什么」）
- 用桩 `wx` 顶掉原生能力（存储 / 弹窗 / 转发 / 触摸注册）
- 再调 `app.touchStart/Move/End` 走**真实触摸分发**

就能从大厅一路点到结算，顺带断言 T-08（敌方棋盘不出现 `plane`/`head` 格）、双棋盘不出屏、
已炸格置灰不可再选、点机头选中 / 再点旋转 / 拖拽落位等关键规则。

`test-layout.js` 解决的是另一类问题：Canvas 界面的溢出与重叠只在特定屏幕上出现，
而手机型号不可穷举。它把 6 种屏宽高代入**真实场景的 `layout()`**，断言每个区块都在屏内、
相邻区块不相交、棋盘格子不小于 30px（触控目标下限）。改布局后先跑它，比在真机上试快得多。

### ⚠️ 写小游戏端测试与交互的四个必踩坑

1. **几何必须在「状态落定之后」再取**。回合切换会连带切换焦点（我方回合 → 敌盘放大 /
   对方回合 → 我盘放大），`applyBattle` 检测到变化会重跑 `layout()`，棋盘的位置与尺寸都变了。
   若提前把 `geo.foeBoard` 缓存下来，算出的像素点会落到别的格子上 ——
   表现为「明明点了机头，却打到了镜像位置」，而且**只在先手是对方时复现**。
2. **别用「累计绘制调用数」做断言**。主循环走 `setTimeout` 兜底，累计值随机器调度抖动会假失败。
   正确做法是清零后渲染一帧，再断言这一帧画了什么（实测 375×667 下一个简单页面单帧约 57 次调用）。
3. **任何点击都必须产生可见反馈**。这是真机验收时暴露最多的一类问题：
   `onTap` 只改了内部变量、界面无变化，玩家一律判定为「按钮坏了」。尤其要警惕
   「作用于下一个」与「作用于已有的」的心智模型错配 —— 参见下方布阵页说明。
4. **拖拽阈值只能有一处**。`app.touchMove` 用 10px 判定 `moved` 并通过
   `onTouchMove(x, y, dx, dy, moved)` 下发给场景；场景若自己再定一个阈值（比如 `u(12)`），
   就会出现「场景认为在拖、app 认为没动 → 抬手又触发一次 tap」的双重语义。
   拖拽落位放在 `onTouchEnd`，而 `tap` 只在 `!moved` 时触发。

### 布阵页：按房间定的架数摆满

核心原则：**手指直接作用在飞机上，不通过按钮中转**。按钮只是快捷方式，不是唯一入口。

架数**在房间页就定死了**（房主选 1 / 2 / 3 架），布阵页不再做这个决定 ——
它只负责「把这么多架摆在我想要的位置」。

- **进页面就自动摆满**，位置随机、互不重叠。不这么做的话，每次开局第一件事就是
  「还差 3 架」，那条提示会变成噪音，而且连点三下「+」纯属重复劳动。
  摆好之后玩家只做调整（拖 / 转 / 收），主动权一点没少。
- **就绪前校验数量**：`activeCount()` 必须**正好等于**房间上的架数，多了少了都不许开局。
  弹窗说清「本局几架 / 你现在几架」，并给一步到位的修法：少了 →「替我补齐」，
  多了 →「收起多的」。两个动作都是玩家点的，补完照样能拖。
- 「收起」不再等于「这一局不用这架」—— 它只是「暂时挪开」，凑不够就开不了局。

| 操作 | 行为 |
|---|---|
| 点棋盘空格 | 在该格添一架，**落点即机头**；放不下也照放，标红（见下节） |
| 点状态条的「+」 | 往棋盘上添一架。落点由系统给（离中心最近的空位），添完立刻选中，方便马上拖 |
| 点机头 | **选中这一架**（整架描边）；点机体也算，命中判定放宽（手指比格子粗） |
| **已选中时再点机头** | 以机头为轴顺时针旋转 90°，机头格不动（这才是「以头部为中心」） |
| **按住机头拖动** | 整架跟着走；原位置**直接空出来**（不留淡影，避免和本体叠成两架），只在落点实时预览，**松手就地落下**（不再吸附） |
| 重叠处再点一次 | 在叠着的几架之间**轮换选中** —— 否则被压在下面那架永远点不到 |
| 选中态下点空白 | 只退出选中，不误放新飞机 |
| 操作栏「旋转」 | 有选中 → 转选中的；否则转最近在场上的一架；一架都没有 → 切换待放朝向 |
| 操作栏第二个按钮 | 无选中 = 「随机布阵」（整盘重排，**总是摆满本局架数**）；有选中 = 「**收起这架**」 |
| 就绪按钮 | 本身是状态指示器：数量不对 → 橙「还差 N 架」/「多了 N 架」；有违规 → 橙「先修正 N 架」；正常 → 「就绪 · N 架」 |

#### 名额数 = 本局架数（1~3 个），三种状态

状态条上的槽数就是本局架数，各代表一架的名额：

| 状态 | 外观 | 点它 |
|---|---|---|
| **未加入** | 灰底 + 淡灰飞机 + **右下角「+」** | 添一架到棋盘（自动找合法位，立刻选中） |
| **收起** | 灰底 + **虚线框** + 35% 不透明度的身份色飞机 | 回到收起前的**原位置、原朝向** |
| **在场上** | 身份色实色飞机 | 选中 / 取消选中 |

三种状态必须一眼分得开：**「+」= 还没用过这一架**，**虚线框 = 用过但拿下来了**，
**实色 = 现在就在场上**。都画成灰底但要靠符号和边框区分，否则玩家会以为飞机被删了。

#### 「收起」而不是「移除」

玩家点「收起」的心态几乎都是「先拿开腾地方，一会儿再放回来」，不是「这局不要这架了」。
所以它只改一个状态位，位置与朝向全留着；但**收起来就凑不够本局架数**，
不补齐是开不了局的 —— 这正是「收起」与「移除」的区别：可逆，但要还。

| | 收起（现在的做法） |
|---|---|
| 飞机数据 | `state = 'off'` 标记，**不从数组里删** |
| 位置 / 朝向 / 编号 / 身份色 | 全部原样留着 |
| 再点回来 | 回到收起前的**原位置、原朝向**（位置现在不合法也照样放回，标红即可） |
| 棋盘上 | 不画、不参与违规判定、不占位 |
| 就绪时 | **会拦截**（数量不够），但弹窗直接给「替我补齐」，一下就能放回来 |

**为什么不 `splice` 掉**：数组下标就是编号。删掉第 2 架，原来的第 3 架会塌成第 2 架，
身份色从紫变青、机头序号从 3 变 2 —— 玩家会以为系统换了他的飞机。
所以名额数组**长度恒定**（等于本局架数，整个布阵期间不变），`state` 说明各自处境，
下标 ≡ 槽位 ≡ 编号，永远是同一件事。

**就绪时有两道关，顺序不能反**：

1. **数量**：`activeCount() === slotCount`，不等就弹 `blockCount`，
   标题是「还差 N 架」/「多了 N 架」，给「替我补齐」/「收起多的」。
   先查数量 —— 数量都不对时去摆位置没有意义。
2. **位置**：不合规（出界 / 压到别人的飞机）弹 `blockStart`，标题是「还有 N 架要调整」，
   给「自动整理」。

两道关都是**拦，不许开局**，但措辞不同：数量不对是「还没对齐房主定的编制」（橙色），
位置不对是「这一架放不下」（红色）。

#### 机头重叠了，怎么知道选的是哪一架

两架飞机的机头落在同一格时，抓手、旋转轴、整架描边全在同一个像素上，
**画面上唯一能区分的只有机头牌里那个数字**。所以三件事同时成立才算可用：

| 手段 | 做法 |
|---|---|
| **看得出这格不止一架** | 机头牌从「色块 + 白字」反转成「**白底 + 红字**」。同一套颜色换正负关系，不用加角标，扫一眼就不一样 |
| **牌上是「当前选中那架」的编号** | 点一下切换，数字跟着变 —— **这是唯一的信号**，所以机头格不画冲突斜线（会划花数字），斜线只留给机身格 |
| **顶部文案说清怎么操作** | 「第 1、2 架机头重叠 · 点该格切换」→「第 2 架已选中 · 此格叠了 2 架，点它切换」 |

**重叠处点按只切换选择，不旋转。** 两个理由：重叠态转完可能还叠着，结果不可预期；
而且轮换和旋转会抢同一个手势，必然有一个永远触发不了（旧代码就是这样，轮换逻辑先吃掉
了「已选中再点」这个条件，**导致重叠的机头怎么点都转不动**）。要转就点操作栏的「旋转」。

**拖动优先抓当前选中的那架。** 否则永远只能抓住后放的那架，先放的怎么拖都拖不动 ——
而重叠恰恰是最需要拖开的时刻。

### 布阵的两阶段：编辑期宽松 · 提交期严格

布阵时**不限制**玩家把飞机摆在哪儿。出界、压到别的飞机，都可以放下去，
只是那一架会被标红。等点「就绪」时统一校验一次：还有不合规的，明确说是哪一架、
为什么，并且**不允许开始游戏**。

**为什么不是「放不下就拒绝」**：

布阵是**多架飞机互相让位**的过程，天然会死锁 —— 想把 A 挪到 B 的位置，得先挪 B；
可 B 想去的地方又被 A 占着。旧做法只剩一条路：先把 A 挪到一个「合法但没用」的位置，
挪 B，再把 A 挪回来。一次调整变成三次，中间那些位置玩家根本不想要。
允许临时非法 = 允许玩家**先拆后建**。

代价是系统不再帮着找位置，所以必须补三件事：

| 环节 | 做法 |
|---|---|
| 合法性**随时可见** | 红格 / 状态条 `!` 徽标 / 就绪按钮直接变成「先修正 N 架」 |
| 提交时**拦住** | 弹窗逐条列出「第 2 架有 4 格超出棋盘」「第 3 架压到别的飞机」，并自动选中第一架问题飞机 |
| 给**显式**的修复入口 | 弹窗里的「自动整理」—— 玩家点了才动他的飞机，而不是拖一下就被系统偷偷改朝向 |

底线只有一条：**机头永远留在棋盘内**。机头是拖拽的抓手，也是「以机头为轴旋转」的轴心，
一旦出界就既看不见也抓不回来。机身可以探出边界（会被裁掉 + 标红 + 说明超界几格）。

> **为什么旋转要「先选中、再点一次」，而不是「点一下就转」**：
> 拖拽的起手式就是按住机头，手指自然会先位移 3~8px。若点一下就转，
> 每次想拖都会先把飞机转歪。选中态是这层安全垫 —— 代价是多点一次，
> 换来的是拖拽不会误触发旋转。

> **为什么不再「点飞机就删除」**：误触代价太高（删掉一架要重放），
> 删除改为选中后点「移除这架」，危险动作单独表态。

### 三架飞机怎么区分

| 手段 | 说明 |
|---|---|
| **身份色** | 第 1 架蓝 `#185FA5` / 第 2 架青 `#14808E` / 第 3 架紫 `#7A5CC4`。刻意避开红（击毁）、橙（命中）、绿（成功）——这三类语义在棋盘上同样要出现，撞色会被误读成「被打中的格子」 |
| **机头序号** | 机头格里印 1 / 2 / 3。颜色负责「扫一眼」，序号负责「确认是它」——只用颜色对色弱玩家无效（男性红绿色弱约 8%），30px 的小格子上相邻色相也很难分 |
| **降饱和聚焦** | 选中 / 拖拽某一架时，其余几架叠一层很淡的灰，焦点那架立刻跳出来（已标红的架不降饱和，它现在最需要被看见） |
| **跨页一致** | 布阵页状态条、棋盘、对战页我方海域用同一套三色 → 「第 2 架」在哪儿都是同一个青色 |
| **对战阶段延续** | 我方海域仍是这三色，所以「哪一架被打残了、还剩几架完好」一眼就知道，不用去数格子 |

> 敌方棋盘**永远**没有身份色（也没有 `plane` / `head` 格），T-08 不变。

### 视觉语言

**非法飞机**（编辑期允许存在，靠它一眼看出来）：

| 部位 | 画法 | 为什么这么画 |
|---|---|---|
| 机体 | **半透明红** `rgba(226,75,74,0.38)` | 面积大，扫一眼就知道这一整块有问题，又不会盖住底下的格线 |
| 机头 | **实色红** `#E24B4A` + 白色序号 | 面积小，必须够硬才认得出来；序号保住了「这是第几架」 |
| 冲突格 | 深红 `rgba(121,31,31,0.5)` + **白色斜线** | 两层半透明红叠一起只会「再深一点」，看不出是**两架**叠在同一格，斜线才说得清 |

**拖拽叠加层**（四种标记，含义不重叠）：

| 标记 | 外观 | 含义 |
|---|---|---|
| `ghostOk` | 实心蓝块 + 实线外轮廓 | **松手就落这里，这一位放得下** |
| `ghostBad` | 浅红块 + 斜线 | **松手也落这里，但放不下**（用斜线而不是纯红块：纯红块容易和「击毁红」混淆） |
| `fade` | 很淡的圆角块 | 拖拽前的原位置 |
| `hint` | 只有虚线外轮廓，不填色 | 「会自动落到这里」。**布阵页已不再产生它** —— 系统不再替玩家找位置；标记本身保留给仍需要建议落点的场景 |

外轮廓是画「一组格子的边界」（只画邻居不在集合内的边），所以 10 格画出来是**一架完整的飞机轮廓**，
而不是 10 个小方框。虚线用 `draw.dashedLine` 手工分段，不用 `setLineDash`（基础库支持不一致 + 测试桩零改动）。

**拖拽手感**：落点用**增量**算（`按下的机头位置 + 手指移动的格数`），不是「手指所在格」。
否则玩家按住机头的下半格时，一开始就会让飞机往上跳一格，手感是「抓不稳」。

### `core/fit.js` 现在做什么

`findFit()` 之前是「放不下就自动吸附到最近的合法位」，那属于**系统替玩家做决定**，
和上面「编辑期宽松」的模型冲突，已经从主流程摘掉了。现在它只剩一个用途：

> 弹窗里那个「自动整理」按钮 —— 把不合规的飞机挪到最近的合法位置。

差别不在算法，在于**谁做决定**：以前是拖一下就偷偷改，现在是玩家点了才改。

`checkAt()` / `occupiedExcept()` / `describeReason()` 仍在主流程里用（判一次合不合法、拼占用格位、生成人话原因）。


### 大厅：最上面是「快速匹配」，按架数拆成三张卡

| 位置 | 入口 | 玩家心里的话 |
|---|---|---|
| 最显眼（第一屏上半部） | **快速匹配 · 1 架 / 2 架 / 3 架** | 我就想马上打一局，打三架的那种 |
| 第二行 | 创建房间 | 我来定规则，等人来找我 |
| 第三行（半宽并排） | 浏览公开房间 / 搜索房间名 | 我想自己挑一间，或者我知道房名 |

匹配被提到最上面，是因为它是**最常用**的入口 —— 大多数时候玩家不想设规则、也不想挑房，
只想打。而它必须按架数拆成三个，因为**架数在进房之后就改不了了**：
不先说清楚，玩家会在布阵页才发现「这局只打 1 架」。

「一键匹配」（不分架数）已经从列表页撤掉了 —— 同样的问题：点下去之前不知道会进多大的局。

### 房间列表：三项信息必须一眼看全

**房间号、架数、每步限时** —— 这三项决定「要不要进这局」，少一项就得点进去再退出来。
私密房在列表里挂「私密」标签，点它先弹密码框。

一屏显示几条**由剩余高度算**，不是写死 6 条：`u()` 按屏宽放大，宽屏上纵向空间并不同比变多，
写死会溢出到底部按钮上；小屏又会浪费整屏。多出来的靠搜索找。

### 房间页：房名 / 飞机数量 / 每步限时 / 是否私密

房间页现在做四件事（加上「等对手」），顺序是「别人怎么找到我 → 打多大一局 → 打多快 → 谁能进来」：

1. **房间名** —— 默认取昵称，点一下可改，最多 12 字。它是别人搜索你的唯一凭据。
   昵称拿法：上次手动设的 → 微信真实昵称（`wx.getUserInfo` 能拿到就用）→「飞行员xxxx」兜底。
   不用 `createUserInfoButton`：那是一块盖在 canvas 上的原生按钮，会挡住界面。
2. **飞机数量** —— 三段控件 `1 架 / 2 架 / 3 架`，默认 3 架。
   它决定这一局多大，也是列表里别人看到的那一项；标在下面的小字直接写「双方都打 N 架」。
3. **每步限时** —— **滑块**，夹在 5~30 秒、**1 秒连续**。
   下限 5 秒是因为再短来不及在 9×9 上打完一炮（选格再确认；双击同格可一步开火）。
   为什么不用 `− ＋` 步进器：26 个档位要按十几次，滑块一次拖到位。
   滑块不注册 `zone`——它按下去就该跳到该位置，注册了 tap 会「按下跳一次、松手又跳一次」。
4. **公开 / 私密** —— 开关**默认关**，也就是默认公开、谁都能看到并进来。
   打开才设 4 位密码。

底部一行把这一局编成一句话回读给你：`3 架 · 每步 20 秒 · 公开`。

> 服务端侧：`room.planeCount` 是**本局架数**（1~3），不是上限。
> `game.deploy` 校验提交架数**严格等于**它，不等直接返回 `PLANE_COUNT_MISMATCH`。
> `room.list` / `room.search` 的列表项也带 `planeCount`，`room.match` 按它筛房 ——
> 「想打 1 架」和「想打 3 架」是两个池子，不能拿 3 架的房去凑 1 架的人。

> 🔐 **密码存在 `games` 集合，不在 `rooms`**。`rooms` 是客户端可读可 watch 的公开视图，
> 密码写进去等于公开。`rooms` 只留 `hasPassword` 布尔，`join` 时由云函数去私有集合比对。

### 出招：选格 → 发射，双击同一格直接开火

默认是两步：点敌盘任意未炸格 → 底下回读「横3，竖4」→ 点「发射」。
多这一步是有意的，**不让手指一滑就打出去**——9×9 上误触一炮的代价太大。

嫌憋屈可以**双击**：同一个格在 300ms 内点两下，第二下直接开火。
选中之后那行坐标后面会写「· 双击发射」，所以它是可见的快捷方式，不是隐藏手势。

判定三条，缺一不可：

- **同一格**。点 A 再点 B 是换目标，手速再快也不开火。
- **300ms 内**。慢了就是「看一眼再决定」，重新选中而已。再短（<200ms）真机上打不出来。
- **上一炮已回来**。`firing` 期间双击无效，否则会出现「选中已经变了、飞出去的还是旧格」。

这条也顺带堵住了一个偏差风险：焦点要从我方切到敌方时棋盘会重新排版，
若第二次点击落在漂移后的位置，就退化成「改选另一格」——不会打错地方。

### 超时：不再跳过回合，改成「替你打一炮」

旧规则是「超时跳过，连超 3 次判负」。问题很实在：两个人都挂机时，棋局靠超时永远推不完；
而且挂机只要熬过 3 次就输，中间那几炮等于白送对手。

现在超时 = **替这名玩家从上到下、从左到右打第一格没炸过的位置**：

- 棋局**一定往前走**，不会僵住
- 落点是**确定**的，不是随机 —— 超时的代价可预期、可复盘（随机等于赌）
- **连续超时 5 次判负**，挂机赢不了；手动出招立刻清零计数

判负前那一炮仍然落地：万一炸中机头，那也是本局最后一炮，规则不能把这一炮吞掉。
界面上，状态条会写「连续超时 3/5」，倒计时最后 5 秒变红，自动打出去那一炮会提示落点。

## 发布流程（正式上架）

本项目目标是**正式上架发布**，小游戏的标准链路：

| 步骤 | 操作 | 说明 |
|---|---|---|
| 1 | 补齐资质 | 小游戏需**游戏类目**资质（软著 / 版号视类目与变现方式而定）；未齐时只能做体验版 |
| 2 | 云环境转正式 | 云开发环境确认已付费/正式，`cloud.js` 填正式环境 ID，重跑 `sync-shared.js`，重传三个云函数 |
| 3 | 上传代码 | 开发者工具「上传」→ 填版本号与描述，成为**开发版** |
| 4 | 设为体验版 | 后台版本管理 → 选开发版设为体验版，加体验成员真机验收 |
| 5 | 提交审核 | 后台提交审核（填功能页面 / 测试账号 / 玩法说明；双人游戏建议备好两个账号给审核员） |
| 6 | 发布 | 审核通过后点「发布」，全量上线；之后每次改动走同样链路 |

上架前自检清单（本项目相关）：

- [ ] `USE_CLOUD: true` 且云环境 ID 为正式环境
- [ ] 云函数 `room` / `game` / `cleanup` 均为最新（跑过 `sync-shared.js` 后重传）
- [ ] `rooms` 集合权限=所有用户可读、仅创建者可写；`games` 集合权限=**所有用户不可读写**
- [ ] `cleanup` 定时触发器已开启（清理超时房间与过期对局）
- [ ] 转发路径在真机上验证：好友点开邀战卡片能直达加入页并回填房间号
- [ ] 真机验证断线重连（60 秒保留）、超时自动轰炸与连超判负（各档 5~30 秒）、投降二次确认
- [ ] 分包 / 包体积检查（小游戏首包上限 4MB）

## 后端方案

**已采用微信云开发**：云函数 + 云数据库实时监听（`watch`），无需自建服务器、无需配置服务器域名。

架构分层：

| 层 | 位置 | 职责 |
|---|---|---|
| 客户端 | `minigame/` | 只做渲染与交互，**不做任何判定** |
| 云函数 | `cloudfunctions/room` | 房间生命周期管理 |
| 云函数 | `cloudfunctions/game` | 布阵校验、开火判定、胜负结算 |
| 公开数据 | `rooms` 集合 | 战况视图，客户端可读、可实时监听 |
| 私密数据 | `games` 集合 | 双方飞机布阵，**仅云函数可访问** |

> 为什么判定必须放服务端：否则客户端可以直接查库看到对方飞机位置，T-08 就形同虚设。
> 详见 [docs/云开发部署说明.md](docs/云开发部署说明.md) 第六节。
