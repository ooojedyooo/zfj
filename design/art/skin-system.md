### 0.1 读法约定：每个数字必须带来源标记（v2.3 新增，全项目规矩）

| 标记 | 含义 | 硬要求 |
|---|---|---|
| **推导** | 由某条约束反算出来的 | 必须附推导链。例：「序号 ≥7:1 → 机头 L\* ≥ 68.2」 |
| **算得** | 由已知值确定性计算出来的（hex → 对比度 / L\*） | 必须写明算法。**不许叫"实测"** —— 它没碰过真机 |
| **量测** | 真机 / 真实出图上采到的 | 必须附测法与样本数 |
| **暂定** | 没有推导，先这样定 | **单独列，不许混在上面三类的位置** |

**为什么要立这条**：v2.1 的机身阶梯 `54/66/46` 混在「ΔL\* ≥ 12」这条真阈值旁边，而它自己最小差只有 8.3 —— 一个凑出来的数伪装成推导值，于是**同一张表里对的那几个也一起失去信用**。危险的不是算错，是**混装**。

最危险的一档是「暂定」伪装成「推导」。本规格 §5.3 的全部相对尺寸（线宽 0.05C/0.028C、圆角 0.10C、后掠偏移 0.37C、喷口 0.40×0.16C、前缘三角 0.16×0.10C）**都是暂定** —— 它们是设计选择，只能靠出图判，不要当推导值引用。

**同一事实写两处，必须配一条机械检查（v2.3 新增）**

本规格里 9 组 `body/head` 在 §3.2/3.3/3.4 的展示块和 §9 的 token 契约块**各写一遍**。人眼比对两个相距几百行的地方是查不出分叉的，必须机械验。

**但这件事一行 grep 干不了，别被一行 grep 骗了。** 两个块的格式不同（§3 是 `body #xxxxxx   head #xxxxxx` 的表格行，§9 是 `{ body: '#xxxxxx', head: '#xxxxxx' }`），所以只能：

```js
// scripts/check-skin-tokens.js（形状，工程落地后接管）
const md = fs.readFileSync('design/art/skin-system.md', 'utf8')
const fromSpec = [
  ...md.matchAll(/body (#[0-9A-Fa-f]{6})\s+head (#[0-9A-Fa-f]{6})/g),   // §3 表格行
  ...md.matchAll(/\{ body: '(#[0-9A-Fa-f]{6})', head: '(#[0-9A-Fa-f]{6})' \}/g)  // §9 契约块
].map(m => [m[1], m[2]])
// 断言：前半 9 组 == 后半 9 组（逐对，不是逐值）
const half = fromSpec.length / 2
assert(fromSpec.length === 18)
assert.deepEqual(fromSpec.slice(0, half), fromSpec.slice(half))   // 规格内部不自相矛盾
// 再 require 真实模块，断言 代码 == 规格
assert.deepEqual(paletteOf(require('.../theme.js')), fromSpec.slice(0, half))
```

**三条要记的：**

1. **必须逐对比较，不能逐值。** 单看"9 个 hex 各出现两次"是不够的 —— `#4789d4` 配错成 `#62c6c3`（2 号机的 head）时，每个值仍然各两次，检查全绿，而配对已经错了。**计数检查抓不到配对漂移。**
2. **检查不能把自身算进口径。** 我第一版就把 9 个 hex 的字面值写进了这条检查里，结果加完当场从 18 次变 27 次 —— 多出来的 9 次是命令自己。所以检查里只能出现 `#[0-9A-Fa-f]{6}` 这种**模式**，永远不出现字面值。**任何内嵌在被检对象里的检查，都要先问一句"它会不会数到自己"。**
3. **它答的问题要选对。** 只验规格内部自洽，只能证明我没写错自己；`require` 真实模块那一半才证明工程没抄错。两个都留。

**临时凭据：已删（本节按约定退场）**

那条 `node -e "...matchAll..."` 的一次性命令已由 `scripts/check-skin-tokens.js` 接管 —— 它同时做了「规格内部自洽」（§3 展示块 vs §9 契约块逐对）和「`require` 真实模块」（`theme.js` 实际导出值与规格逐对），还多带一条本文件 sha1 指纹校验，指纹不对直接 exit 2。

留一句教训，因为删掉的只是命令，不是教训：**临时凭据必须写清"被谁接管、哪天移交"**。写「本节删除」是不够的 —— 没有主语的删除令永远不会被执行，它只会从"待办"变成"遗忘"。所以那句命令的墓志铭要带名字：*由 `scripts/check-skin-tokens.js` 于 PR-4 接管*。

**凭据必须带版本指纹。** 行号是文件版本的函数：任何一次编辑都会让行号失效，而读凭据的人没有理由怀疑一个自己没改过的文件。所以行号只能配 `sha1` 一起用 —— 否则「全对」可能对的是一个已经不存在的版本。

**「待落」必须写清 谁 / 何时 / 哪个文件。** 否则它只是把完成体换了个说法，问题没解决 —— 「落成 `check-skin-tokens.js`」这类说法的病根就在这：它没说谁在什么时候把什么放进哪个路径，于是它可以一直"正在进行中"。

## 1. 现状审计

### 1.1 先纠正两个事实（影响工程量估算）

| 任务书里写的 | 代码里的实际 | 影响 |
|---|---|---|
| 飞机约 **3 格宽** × 4 格高 | **5 格宽 × 4 格高**（`planes.js`：机翼行 `[1,0]..[1,4]`） | 可用画布 180×144px（390 屏），比预想宽 66%。**细节预算宽松，不必抠到 1px** |
| 390 屏约 32px/格，320 屏 30.4px/格 | 390 屏 **≈36px**，320 屏 **≈30px**（`maxBoardW = W − u(80) − u(22)×2`，再 /9） | `30px` 是设计的**下限基准**，所有线宽按 30px 起算并加下限保护 |

飞机真实几何（机头朝上，`■`=占格）：

```
      ■            row0  机头 1 格
    ■■■■■          row1  机翼 5 格
      ■            row2  机身 1 格
```

## 2. 皮肤抽象层：可换 / 不可换

### 2.1 判定原则

1. **语义优先**：任何承载"这一格发生了什么"（击毁/命中/未命中）的元素，颜色不可换。皮肤换环境，不换事实。
2. **可读性下限**：皮肤可以更暗、更暖、更花，但不得让任何一项已验收的对比度掉到门槛以下（§3.5）。
3. **换肤不得改变信息通道的数量**：机头序号、双轴刻度、空格微点 —— 是功能不是装饰，不能删、不能弱化。

### 2.2 可换（皮肤 token，键名对齐工程）

| 元素 | 工程键名 | 约束 |
|---|---|---|
| 页面背景 | `bgTop` `bg` `bgBottom` `bgGrid` | 与 `text` ≥ 12:1 |
| 面板 / 卡片 | `panel` `panelHi` `card` `border` `borderHi` `gray` `sheen` `shade` | 与 `textMuted` ≥ 4.5:1 |
| 底板 | `plate` `plateShadow` | 外框/底板 ≥ 1.8:1；`plateShadow` 允许是 rgba |
| 格线 | `grid` | 格线/底板 **1.3~2.0:1**。高于 2.0 就变成表格，会盖过空格微点 |
| 双轴刻度 | `axis` | 刻度/底板 **≥ 4.5:1**（A2 就是踩了这条） |
| 空格微点 | `cellDot` | rgba，透明度 0.18~0.22 |
| 文字三级 | `text` `textMuted` `textFaint` | 见 §3.5 |
| 飞机身份色 | `palette[i].body` `.head` `.glow` `.outline` | **色相必须落在 165°–345°**，三组互隔 ≥ 30° 且明度阶梯 ≥ ΔL\* 12 |
| 机头序号字色 | `headInk` | 与 `palette[i].head` ≥ 7:1 |
| 强调 / 交互色 | `primary` `primaryDark` `primaryInk` `selectRing` `hintRing` `ghostOk` | **不得进入格子内部**（只出现在格外的环、按钮、示踪线上） |
| 未命中标记（请求新增） | `miss` `missRing` | 中性低彩；≥ 2.5:1。它是"无信息"的标记，一旦有彩度就会被读成某种状态 |
| 扫掠 | `sweepColor` `sweepGlow` | 冷白系；**不用 additive 混合** |

### 2.3 永远不可换（写死，不接受皮肤覆盖）

| 元素 | 值 | 理由 |
|---|---|---|
| **红 = 击毁 / 危险** | `#FF5A5A`（浅底 `#3A1620`，亮字 `#FFB0B0`） | 全游戏唯一的"你输了这一格"信号。改红 = 玩家要重新学一遍规则 |
| **橙 = 命中** | `#FF9B2F`（浅底 `#3A2614`，亮字 `#FFC77A`） | 同上 |
| **绿 = 成功 / 就绪** | `#45E08A`（浅底 `#12321F`） | 同上。A1 的根源就是身份色侵入了它的色相带 |
| **机头格印序号 1/2/3** | 字号 0.52C / weight 600 / `headInk`，对比 ≥ 7:1 | 「这是第几架」的**权威通道**，是身份凭证不是装饰 |
| **已炸格必须明显区别于未炸格** | §4.8 判据 | 否则"我打过哪几格"要靠记忆 |
| **可点击格提示（空格微点）** | `cellDot`，位置恒在格心 | 深底大格上，纯网格会读成"空表"而不是"可操作区域" |
| **双轴 1-9 刻度** | 位置固定在底板外环带 | 「横3，竖4」这套报点口径的唯一物理载体 |
| **语义色明度排序** | 击毁红 L\* > 命中橙 L\* > 未命中灰 L\* | 破坏排序会出现"炸过的比刚打中的还亮"这种反向暗示 |

### 2.4 色相禁带（本规格最有用的一张表）

| 区间 | 归属 | 允许？ |
|---|---|---|
| 345° – 20° | 红（`danger #FF5A5A` = 0°） | **禁** |
| 20° – 50° | 橙（`hit #FF9B2F` = 31°，`warn #FFB84D` = 36°） | **禁** |
| 50° – 120° | 黄 / 黄绿 | **禁**（夹在橙与绿之间，会被读成"某个我没见过的状态"） |
| 120° – 165° | 绿（`success #45E08A` = 147°） | **禁** |
| **165° – 345°** | **青 → 蓝 → 紫** | **唯一允许带** |

**v2 新增一条硬规则：身份色相是全局常量，三套皮肤共用 `212° / 178° / 285°`，皮肤只调饱和度与明度。**

三个好处：① 玩家换皮肤后"2 号机还是那个青"的肌肉记忆还在；② 对比度表只需验一次色相关系；③ 工程的 `palette` 结构天然支持（同 hue 不同 L/S）。

三条补充：

- **三组互隔 ≥ 30°，且必须同时给出明度阶梯（机身 L\* 差 ≥ 12）。** 色弱玩家（红绿色盲占男性 8%）在 178° 和 212° 之间会犹豫，明度阶梯是给他们的第二通道。
- **色彩是加速通道，序号是权威通道。** 冲突时以序号为准 —— 所以序号永远不许消失。
- `primary`（强调色）与某个身份色**允许色相接近**，因为它从不填充格子，只做 1~2px 的环与按钮，靠**形状 + 明度**（比身份色亮 ΔL\* ≥ 20）区分。这条是有意的，不是遗漏。

## 4. 雷达扫描动效规格（v2：零 clip 几何）

### 4.1 形状：为什么是"扇形旋转扫掠"

| 方案 | 判断 | 理由 |
|---|---|---|
| **A. 扇形旋转扫掠**（采用） | ✔ | ① 与 9×9 方格的**几何同构**（都是从中心向外辐射的读法）；② 中心匀速旋转 → 边缘线速度大、中心小，每格**驻留时间天然不同**，读起来是"活的东西在动"；③ 一圈自带节奏，不用任何 easing |
| B. 水平扫描线往返 | ✘ | 核心读法是**按行报点**（"横3，竖4"）。水平线来回扫会与"行"结构争注意力，折返点天生像卡顿 |
| C. 同心圆扩散 | ✘ | 没有方向性，看不出"在扫描"只有"在呼吸"；重复叠加后会让玩家产生"又过去了、还是没东西"的焦躁。而且圆扩散与方格盘的边角关系很别扭 |

只做**一层**扫掠，不做"主扫 + 副扫"（两层立刻变成"特效"，违背克制）。

### 4.2 几何（v2：外沿就是棋盘的四条边）

| 参数 | 值 | C=36 / S=325 时 | 说明 |
|---|---|---|---|
| 旋转中心 | 棋盘**几何中心** | `(cx, cy) = (m.x + 4.5C, m.y + 4.5C)` | 9 是奇数，中心落在**正中那一格（row5,col5）的格心**上 |
| 半边长 `half` | `m.size / 2` | 162px | — |
| 外沿 | **棋盘四条边**（不是圆弧） | — | 射线与正方形求交，距离在 `162 ~ 230px` 之间随角度变化（角上最远） |
| 内半径 r₀ | **无** | — | v1 的挖洞是为了防「嵌套填充在圆心汇聚成风车」；v2 的拖尾是**并列扇段、互不叠加**，圆心不会累积，风车不存在 |
| 总跨度 | **75°** = 核心 40° + 拖尾 35° | — | 90° 太糊（四分之一盘都亮），60° 太窄像激光。**总跨度不是第三个常数，是 `arc + trail × seg` 算出来的** —— 写成独立数字就一定会漂，v2.4 之前它就漂成了 80° |
| 拖尾层数 | **7 层 × 5°**（v2.4 定案，原写 8 层） | — | 见 §4.4 的条带计算：**少于 7 层就出条带**。第 8 层 α=0.001 ≈ 0.26/255，低于 8 bit 量子，**永远渲染不出来** —— 留着它只会让「契约写的」和「屏幕上的」差一层 |
| `SWEEP.anchor` | **`'board'`** | — | 拒绝 `'page'`：盘外扫进来后半个周期都得做遮罩，而正方形内截几何是相对盘定义的 |

**为什么"正方形内截"比"圆扇形 + clip"更好，不只是因为没 clip**：

1. 圆弧外沿会让光束的尖端在盘面上**描出一个内切圆**（如果按工程说的把半径限制在内切圆）。那个圆会变成一条可见的边界，暗示"角落扫不到" —— 而在一个每格都等价可炸的盘上，这是**假信息**。
2. 正方形内截的外沿贴合棋盘边界，读作"光在方形舷窗后面转"，几何上自洽。
3. 中心到边界的距离随角度变化（162→230px），尖端在角上走得快、在边中走得慢 —— 这层微妙的非匀速让旋转**不像机械转盘**，是白送的好处。

### 4.3 角速度与时间

| 参数 | 值 |
|---|---|
| `SWEEP.speed` | **45°/s** |
| 一圈 | **8.0s** |
| 加速/减速 | **无，严格匀速**。仪器的可信度来自"它不需要讨好你" |
| 方向 | **顺时针**（canvas y 轴向下，角度递增 = 视觉顺时针） |
| 相位来源 | **全局单调时钟，永不复位**：`θ = (battleClock / 1000 × 45) % 360`，`battleClock` 在 `update(dt)` 里累加，**不管是等待态还是我方回合都照常累加**。不用 `Date.now()`（墙钟与动画无关，取模会乱跳），也不在状态切换时清零 |

> **v2.1 更正**：v2 写的是"从进入该状态起累计"，那是错的。一局里"对方回合"要反复进出十几次（每回合切一次），每次从 `t=0` 起算 = 雷达每 20 秒从 12 点重新开机，比相位跳变更刺眼。正确做法是**一个永不复位的时钟 + 240ms `masterAlpha` 淡入遮住入场**：玩家每次看到的都是"这台雷达一直在转，只是刚才没显示"，而不是"它每次都重新启动"。
>
> 用 `dt` 累加（不是 `Date.now()`）还有一个必要副作用：切后台再回来，`dt` 不会一次性跳过几秒，相位不会瞬移。

为什么不更快：雷达 2s 一圈是"扫描"，8s 一圈是"守夜"。我们要后者 —— 玩家在等对方出手，这 20 秒里屏幕不该催他。

### 4.4 拖尾衰减（v2：透明度阶梯直接硬编码）

沿角度方向，k = 0 在前沿、k = 1 在尾端：

```
α(k) = 0.10 × (1 − k)^1.6
```

因为拖尾是 **8 个并列扇段**，直接在代码里写死 8 个数，不需要运行时算幂：

| 层（从核心往外） | 0 核心 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|---|
| 覆盖角度 | 40° | 5° | 5° | 5° | 5° | 5° | 5° | 5° | 5° |
| `globalAlpha` | **0.100** | 0.090 | 0.072 | 0.055 | 0.040 | 0.027 | 0.016 | 0.007 | 0.001 |

> **不要从这张表抄数。** 权威值是 §9 的 `SWEEP.ahead`（**7 位**，v2.4 已删掉末尾 0.001）。本表保留只为展示 Δα 的推导过程 —— **权威值只留一处，其余处指向、连抄都不抄**。

**为什么至少要 7 层而不是工程默认的 4 层** —— 相邻层透明度差太大会在暗底上显出"切面"：

| `SWEEP.trail` | 每层角宽 | 相邻最大 Δα | ≈ 8bit 级数 | 判断 |
|---|---|---|---|---|
| 4 | 10° | 0.0336 | 8.6 / 255 | **看出切面**，像一块切开的玻璃在转 |
| 5 | 8° | 0.0280 | 7.1 / 255 | 仍偏硬 |
| 6 | 6.7° | 0.0239 | 6.1 / 255 | 临界 |
| 7 | 5.7° | 0.0208 | 5.3 / 255 | 大致安全 |
| 8 | 5° | 0.0185 | 4.7 / 255 | **上界**，v2.4 之前被当成"采用"；实际落地见下方「定案」 |
| 10 | 4° | 0.0150 | 3.8 / 255 | 更稳，但每帧多 2 次 fill |

**v2.4 定案：落地 7 层 × 5° = 35°，总跨度 = 40 + 35 = 75°。** 依据是**实际阶梯**，不是上表的 N：

- `ahead` 相邻最大差 = `0.090 − 0.072` = **0.018**（≈ **4.6 / 255**）。它出现在最亮的两层之间，**与总层数无关** —— 只要阶梯头两格是这两个值，这个台阶就存在。
- 第 8 层只贡献 `0.007 − 0.001` = 0.006 的台阶（1.5/255），而它自己的 α = 0.001 ≈ 0.26/255 **低于 8 bit 量子**，任何 dpr 下都渲染不出来。
- 所以第 8 层是纯账面上的：删掉它，屏幕上零变化，契约与实现差一层的问题消失。

上表那张 "N → Δα" 的对应关系是 v2.1 按 `peak × (1−k)^1.6` 中点采样算的，**用来回答"至少几层"**；真正决定落地值的是阶梯本身。两件事别混着用。

**关于"阈值"要说实话（v2.1 更正）**：v1 里我写的"阈值约 0.018"不是实测值，是**从错误的 Δα 反推出来的** —— 当时以为 N=6 是 0.045。工程复算后真实值是 N=4 → **0.0336**、N=6 → **0.0239**。上表全部按中点采样 `peak × (1−k)^1.6` 重算过，与工程的复算一致。

所以别把它当物理常数。正确的决策方式不是"赌阈值"，而是看成本：**每多一层只花 1 次 `fill`**。落地取 **7 层**（见上方「定案」），代价 7 次 fill ≈ 一帧的 4%（§6.1）。**别省到 6 层以下**：6 层的相邻最大差是 0.0239（6.1/255），暗底上能看出台阶。

v1 里那条"径向衰减 f(r)：内弱外强（0.55→1.0）"在 v2 **删除**：
- 它的原始目的是防止圆心过曝（圆心是四格交汇的视觉十字路口）。圆心过曝只在**嵌套填充**时发生，v2 是并列扇段，不存在。
- 单次 `fill` 无法表达"角度 × 径向"二维衰减，硬做要拆成内外两圈 = 填充数翻倍，收益 < 成本。
- 外沿已被棋盘边界自然截断，"越远越弱"的需求本来就下降了。

### 4.5 图层插入位置（最重要的一节）

**从上到下绘制顺序（L0 最先画）**：

| 层 | 内容 | 静态/动态 |
|---|---|---|
| L0 | 页面背景三段渐变 + `bgGrid` | 静态 |
| L1 | 底板 `plateShadow` → `plate` → `frame` 描边 | 静态 |
| **L2** | **雷达扫掠：核心扇段 + 8 段拖尾 + 前沿线 + 束头** | **动态** |
| L3 | 网格线（10 横 + 10 竖 = 20 条）+ 棋盘外沿加粗框 | 静态 |
| L4 | 空格中心微点（81 个一次 fill） | 静态 |
| L5 | 双轴刻度 1-9 | 静态 |
| L6 | 飞机 10 格 + 全部装饰层 + 机头序号 | 静态 |
| L7 | 命中 / 未命中 / 击毁标记 | 静态 |
| L8 | 叠加层（select / ghostOk / ghostBad / fade / hint） | 半动态（仅拖拽中） |
| L9 | 页面 UI（标题、状态条、倒计时、按钮） | 静态 + 文字每秒变 |
| L10 | 全局浮层（toast / busy） | 动态 |

三条必须理解的顺序决定：

1. **扫掠在格线之下。** 格线保持在最上层。反过来，扫掠每经过一次就把 20 条格线洗淡一次，9×9 的边界会周期性变模糊 —— 而"数格子"是高频动作。
2. **扫掠在所有内容之下。** 于是它**物理上不可能**盖住机头序号、命中橙点、击毁红叉、飞机。硬约束「语义色不可被皮肤吞掉」在这里不是靠"调低透明度"保证的，是靠**图层次序**保证的 —— 这才是可靠的保证方式。（也因此 §4.8 那条"不碰已炸格"**一行特判代码都不用写**。）
3. **空格微点在扫掠之上。** 微点是"这里能点"，是交互语言；扫掠是环境光。环境光不许压过交互提示。

**副作用（要接受）**：被占用的格子（飞机、命中、未命中、击毁）会遮住扫掠，光线在这些格子后面断掉。这读起来是"光从物体背后扫过去"，物理上通，而且强化了"盘上放着东西"的实体感。**不要为了连贯去反向补光**（那才会毁掉可读性）。

### 4.6 边界处理（v2：无 clip，几何自截）

- **不用 `ctx.clip`。** 扇段的路径在构造时就沿棋盘四条边收口，从不越界 —— 见附录 B 的 20 行实现。
- **这也顺带解决了刻度保护**：刻度画在底板外扩的 `PAD` 环带里（`PAD = 22`）。v1 用 clip 是为了防止扫掠去洗那 18 个 9~13px 的数字；v2 的外沿用 `half = m.size/2`，天然停在格区边界，**扫掠永远出不了格区**，数字扫不到。
- 不需要圆角处理：格区四角是直角的，底板圆角（`radius.lg`）在格区之外，两者本来就不相交。
- 相邻扇段共享完全相同的边顶点 → 无缝、无累加、无暗线。

### 4.7 启停时机

| 场景 | 状态 | 扫掠 | 理由 |
|---|---|---|---|
| 大厅 | — | **关** | 没有棋盘。大厅氛围靠 `bgGrid` 就够；再加动效只让首屏更费电 |
| 房间列表 / 创建 / AI 调参 | — | **关** | 全是要读的表单 |
| 布阵 | 编辑中 | **关** | 全游戏认知负荷最高的一页：要判断 5 格宽机翼的边界、在 30px 格子上对准拖拽。任何运动元素都让"落点在哪"多花一次确认 |
| 对战 | **对方回合 / 等待回应** | **开**（仅当前放大的那块盘） | 全游戏唯一"玩家没事干"的 20 秒。静止的盘 = 玩家怀疑卡死；扫掠 = "系统在跑、我们在听"。此时没有读数任务 |
| 对战 | **轮到我方出手** | **关** | 要逐格排查、核对"横3竖4"、点选目标。**读数优先于氛围**，不可协商 |
| 对战 | 已结束 / 跳转中 | **关** | — |
| 结算 | — | **关** | 要看清结果 |

**"只扫一块盘"**：同一时刻最多 1 个扫掠实例，挂在**当前放大的那块盘**上。
① 两块盘同时扫，视线会被两个不同相位的运动撕开（最难受的一种视觉噪声）；② 缩略盘格子只有 11px，按 §6.4 本来就该关掉。

**启停过渡**：硬开关会让"轮到你了"的瞬间像掉帧。给整层一个 0~1 的主透明度 `masterAlpha`，**240ms 线性过渡**；过渡期间相位照常推进，再进入时不会看到"从 0° 重来"。`masterAlpha === 0` 时**整层跳过，0 次绘制调用**。

### 4.8 与「已炸格」的交互

**结论：不加亮、不特殊处理、不改变任何已炸格的色值。**

1. **会破坏"亮度 = 可操作性"的既有约定。** 现在盘上暗 = 已处理（击毁格靠红不靠亮度），亮 = 可操作。给已炸格加亮等于说"这里还能打"。
2. **违背语义色的独占性。** 已炸格的颜色（miss 灰 / kill 红）是"事实"，让氛围改变它的明度 = 让氛围参与陈述事实。
3. **在 §4.5 的图层次序下这件事自动成立**：扫掠在 L2，已炸标记在 L7，扫掠根本到不了它。**不需要任何特判代码。**

唯一可见的交叠是**前沿线从已炸格上划过去** —— 那是"光束位置"，不是"这一格的状态"。

> 验收时专门看一眼：在 10 个已炸格的盘上扫一圈，如果任何瞬间你觉得"那格好像变亮了一点、是不是又能打了"，方案就是错的。

### 4.9 视觉强度：判断是「克制」，并且有数值依据

**峰值 `A_peak = 0.10`。上限 0.12，超过 0.14 不接受。**

| A_peak | 空格亮度 L\*（空盘 9.4） | 抬升 ΔL\* | 未命中点 vs 该空格（静止时 3.35） |
|---|---|---|---|
| 0.04 | 13.5 | +4.1 | 3.04 |
| 0.06 | 15.4 | +6.0 | 2.89 |
| 0.08 | 17.2 | +7.8 | 2.75 |
| **0.10** | **19.4** | **+10.0** | **2.58** |
| 0.14 | 23.0 | +13.6 | 2.30 |
| 0.18 | 26.9 | +17.5 | 2.01 |

读法：未命中点与底板是 3.35:1，这是它"能被看见"的余量。扫掠每抬一次底板，余量就被吃掉一截。0.14 时只剩 **2.30** —— 一个 3.8px 的灰点压在提亮的底上，强光下玩手机就开始指望不上。而"我这格打过没有"是**每回合要判断 9 次**的动作。

**要接受的事实：这个强度下，扫掠是"隐约可感"的。** 静态截图里几乎看不出来，只有连续播放才感到"盘在呼吸"。这正是要的效果 —— 玩家事后描述它时应该说的是"盘好像是活的"，而不是"盘上有个光在转"。

**运动感的来源是前沿线，不是扇面**：
- 前沿线：1px，`0.20`（比扇面亮一倍），从中心画到边界点
- 束头：在边界点画一条**垂直于半径的 3px 短线**，`0.30`。横杠读作"扫描头"，圆点会被读成"敌机"—— 后者会误导

### 4.10 实现要点

```js
// 放在 board.js render() 的 L2 位置
const sw = o.sweep                       // { t, alpha } | null
                                        // t = 全局 battleClock（毫秒），永不复位，见 §4.3
if (sw && sw.alpha > 0 && cell >= SWEEP_MIN_CELL) {
  const cx = m.x + m.size / 2, cy = m.y + m.size / 2, half = m.size / 2
  const th = ((sw.t / 1000) * SWEEP.speed) % 360      // 度
  const a  = th * Math.PI / 180                      // 前沿角（弧度）
  const CORE = SWEEP.arc * Math.PI / 180
  const SEG  = 5 * Math.PI / 180
  const TRAIL = [0.090, 0.072, 0.055, 0.040, 0.027, 0.016, 0.007]  // 第 8 层 α=0.001，省

  ctx.save()
  ctx.globalAlpha = sw.alpha                          // 240ms 过渡的主透明度
  ctx.fillStyle = sweepColor
  ctx.globalAlpha *= SWEEP.peak; wedgePath(ctx, cx, cy, half, a - CORE, a); ctx.fill()
  for (let i = 0; i < TRAIL.length; i++) {
    ctx.globalAlpha = sw.alpha * TRAIL[i]
    const b = a - CORE - SEG * (i + 1)
    wedgePath(ctx, cx, cy, half, b, b + SEG); ctx.fill()
  }
  // 前沿线 + 束头（换回不透明度的基准）
  ctx.globalAlpha = sw.alpha
  edgeLine(ctx, cx, cy, half, a, 0.20)                // 1px，到边界点
  headTick(ctx, cx, cy, half, a, 3, 3, 0.30)          // 垂直短线，沿半径内移 3px（见下）
  ctx.restore()
}
```

需要写死的实现约束：

- **束头（横杠）沿半径内移 3px**，画在 `boundaryAt(θ) − 3` 而不是 `boundaryAt(θ)`。外沿边界点正好压在格线上，一条 3px 的横杠居中画上去会骑在格线上、糊成一坨。内移 3px 之后它是"悬在光带尽头的一小段亮线"，读作扫描头。前沿线（1px）不受影响，它可以顶到边界。
- **外沿没有弧，所以没有弦高误差。** 工程按"8° 段用直线代替弧"算出弦高 0.57px —— 那是**圆弧近似**的误差。本方案的路径顶点全部落在正方形四条边上（`edgePoint` 定义如此），顶点之间要么在同一条边（直线就是边本身，误差 0），要么跨角（插角点后仍是两条边，误差 0）。**所以弧一次都不需要画**，那 0.57px 可以完全不要。
- **禁止 `globalCompositeOperation = 'lighter'`。** 部分安卓 GL canvas 上设备相关，会导致"同一份代码 A 机 0.10、B 机 0.25"，§4.9 整张表作废。用默认 `source-over`。
- **禁止 `shadowBlur` / `filter`。** 与全仓既有约定一致（`draw.js` 用"偏移块"替代 `shadowBlur`）。
- **禁止 `createConicGradient`**（基础库不可用）和 **`setLineDash`**（`draw.js` 已验证部分安卓为 iOS 空实现）。
- 前沿线/束头的透明度用 `strokeStyle = 'rgba(r,g,b,0.20)'` 独立给，**不要叠在 `globalAlpha` 上**，否则会和过渡期透明度相乘（过渡期会变成 0.2 × 0.5 = 0.1，暗得看不见）。
- 整个扫掠层只涉及路径填充，`save/restore` 成对，无 state 污染。

### 4.11 无障碍：减少动态

系统开启「减少动态效果」时：

- **扫掠直接关闭（`masterAlpha` 恒 0）**，不提供"更慢的扫掠"版本。
- 理由：对前庭敏感人群，**慢速大范围旋转比快速旋转更糟**（视野边缘缓慢移动的物体是最强的眩晕诱因）。"减速"看起来更友好，实际上最坏。
- 替代：不加任何补偿动效（状态条里 `对方行动中…` 已经是静态文字）。不花钱、不犯病。
- 要接进 `design/accessibility-requirements.md` 的动效条目：**「全屏旋转类动效可关闭，关闭后信息零损失」** —— 本方案的扫掠不承载任何信息，可以放心声明。

## 5. 飞机精美化画法

### 5.1 两条统治性约束（所有数字都是在它们之下妥协出来的）

> **① 不许向外长**：装饰不得越出这架飞机的 10 个占用格。
> 越界 → 玩家把空格读成"这里也有飞机"，而机头被击中 = 整机摧毁，读错一格就是读错一条命。
>
> **② 不许向内削**：不许出现"往底板方向压暗/收缩"的形变。
> 削出缺口 → 那格读起来像"空的"，同样致命。
>
> **推论**：精美化只能靠 ① 内部明暗结构 ② 亮色细线 ③ 描边。这就是为什么下面 5 层里 4 层是"线"而不是"形"。

### 5.2 机体的真实几何

```
col:   0    1    2    3    4
row0             ■                 机头 1 格（唯一，正中）
row1   ■    ■    ■    ■    ■       机翼 5 格（全宽）
row2             ■                 机身 1 格
row3        ■    ■    ■            机尾 3 格（居中）

★ col2 在 row0~row3 四行全部占满 → 一条 1×4 的连续竖条 = "龙骨"
```

**这是整份规格最关键的一条观察。** 现状读成"加号"，就是因为没人用这条贯通的中轴 —— 一个没有脊梁的十字，本来就长得像加号。加上龙骨之后，同样的 10 个方块立刻变成"一根有翼的东西"。横向 5 格（180px）也意味着细节预算很宽松：翼展里放两条后掠线，间距 45px，一点不挤。

### 5.3 分层清单（键名对齐 `palette[i]`）

|---|---|---|---|---|---|---|

| 8 | **翼尖灯 ×2** | 直径 0.055C，下限 1.6px | 2.0px | `planeArt.light` | 1 fill（一条路径两个圆） | 是 |

> **为什么装饰色是 `planeArt.*` 共用、而不是 `palette[i]` 每架一套**（v2.1 改了 v2 的写法）：
> 镜面高光本来就该是**中性色**。紫机身上打一层中性高光，比打一层紫高光更像金属；三架用同一套装饰色，机身色相的辨识度反而更纯粹（一架飞机只有 `body`/`head` 两个色值是有彩的）。
> 附带好处：§5.8 的受损混色只需要改一个 `strokeStyle`，不用遍历三架。
> 工程早先的契约里给了 `palette[i].glow / .outline`，他复核后自己也判定那是错的，我们结论一致。

**合计 13 次绘制调用/架**（现状 10 格 = 10 fillRect + 1 text = 11）→ **净 +2**。加可选投影 → 15。

### 5.4 每层的设计理由（不只是"好看"）

**#1/#2 双层描边（暗 1.8px + 亮 1.0px）**
单层白描边只告诉你"这里有边界"，不告诉你边界往哪边倒。暗底 + 亮面 = 一圈 0.8px 暗边压在外面，飞机从底板上"浮"起来一层。路径建一次、stroke 两次（Canvas 路径在 `beginPath` 前一直有效）。**全套方案里性价比最高的一层，务必先做它。**

**#3/#4 底色合并成两条路径**
现状逐格 `fillRect` = 10 次调用。8 个机体格颜色完全相同 → 拼成一条路径一次 fill。零视觉差异，省 8 次，正好抵掉新增装饰的一半开销。

**#4 机头底色：它是座舱盖，不是一块白牌（v2.2 重写）**

先说失败案例，因为它界定了这条规则。v2.1 为了统一色相，把三个 `head` 都做成了**近白**：abyss `#d6dde7`（L\* **87.9**）、dusk `#d7dee5`（L\* **88.1**）、mono `#fcfcfd`（L\* **99.0**，就是白）。三者的色相其实还在（215° / 176° / 240°），但**到了这个亮度上已经装不下彩度了** —— abyss 的机头彩度被压到 26%，只剩机身的 42%。两个后果：

1. **36px 上**：机头 L\* 87.9 vs 机身 54.3 —— 差 33.6 级，一块白把机头和机身**割成两个物体**，读起来像贴上去的标签。
2. **11px 上**：它成了整个盘上最亮的元素，读成"空格 / 缺口 / 被标记"，飞机散成一堆色块。

所以 `head` 的定义改成三条，全部可验算：

| 约束 | 值 | 为什么是这个值 |
|---|---|---|
| **色相** | == `body` 的色相（偏差 ≤ 3°） | 换肤只许改"照得多亮"，不许改"什么材质"。去色相就是换材质 |
| **彩度** | `body` 彩度 × **0.75**（验收带 0.70~0.85） | 受光面会**变亮 + 轻微洗淡**，但绝不能洗成中性。旧值只有 42% 且亮度冲到 L\* 88 → 白牌；新值 75% 且压在 69~74 → 座舱盖 |
| **L\*** | `clamp(body_L* + 14, 69, 74)` | 下界 69 是**序号 ≥7:1 反推出来的**（近黑 ink 在 L\* 68.2 才刚够 7:1，取 69 留余量）；上界 74 是"不许发白" |

**下界 69 不是审美，是算出来的**：abyss 的 `headInk #04121F` 要拿到 7:1，机头亮度必须 ≥ L\* 68.2。这条约束一确定，`head` 就只能在 [69, 74] 这个 5 级宽的窄窗里选 —— 这也是为什么三套皮肤九个机头全部挤在 69.1~74.1。

**由此产生一个必须承认的不对称**：机身越亮，机头能提的越少。

- 1 号机（机身 56）→ 机头 70，Δ14：读得很清楚
- 3 号机（机身 43.5）→ 机头 69，Δ25.5：提得最多，但仍是饱和紫罗兰，不是白
- **2 号机（机身 70.1）→ 机头 74.1，Δ 只有 4.1**：这是窗口的必然结果，不是配错色

2 号机的补偿有两条：彩度从 62% 降到 47%（肉眼看得出是"更浅的那一种青"），以及它的方向本来就由 序号 + 龙骨亮端 + 并集轮廓 三条通道给足。**不要为了把 Δ 做大去动 2 号机的机身** —— 它卡在 70 是为了给阶梯让出 14 和 27 两段，一动全塌。

**C < 22px：不画机头底色（v2.2 新增）**

```js
if (C >= HEAD_PLATE_MIN_CELL) {      // = 22
  fillPath(headCellPath, palette[i].head)   // 座舱盖
} else {
  // 机头格与机身同色 → 整架只剩 1 次底色填充，是一个完整的同色剪影
  fillPath(headCirclePath, headInk)         // 方向靠这个点
}
```

圆点：半径 `max(1.2, 0.13C)`，色 `headInk`，画在机头格几何中心。

- **为什么是暗点不是亮点**：亮点在小尺寸读成"高光 / 空洞"（就是白牌那个病），暗点读成"标记"。而且 `headInk` 对机身的对比已经算过，最低 3.1（dusk 3 号机），满足 WCAG 非文字 3:1；亮点拿不到这个保证 —— 机身亮的那两架（L\* 70）配亮点什么也读不出来。
- **这一档飞机的方向其实主要由剪影给**：机头是唯一 1 格宽的前伸，机翼 5 格、机尾 3 格。11px 下剪影比任何装饰都稳。**旧的白牌不是在帮忙，它是在破坏剪影** —— 一块亮格让 10 格散成"机身 + 一个亮块"。圆点是剪影之上的保险，不是主力。
- 参数挂 `HEAD_PLATE_MIN_CELL = 22`：**独立常量、有意与 `AXIS_MIN_CELL` 同值**。理由不同 —— 刻度/微点是「读不了就没意义」，机头底色是「序号没了，它的浅底就没存在理由」。复用同一个常量会让将来有人调刻度阈值时机头底色**静默跟着动**，代码上看不出是被牵连的。

**#5 龙骨（核心）**
一条 0.30C 宽的竖直渐变带，纵跨 4 格，从机头端到机尾端衰减到 7%。
- 为什么方向就是"机头方向"：渐变亮端永远在 local 的 −Y 端，而 −Y 端永远是机头（§5.5）。**朝向被画进了光照里**，玩家甚至不用看序号 —— 第二重方向编码。
- 为什么 0.30C（10.8px）：宽到能读成"一条带"，窄到不会让机头格看起来被切成两半。0.5C 以上会有一条亮带穿过序号；0.2C 以下在 30px 屏上只剩 6px，退化成划痕。
- **必须让位**：龙骨画在序号**之下**；若该机头格画了"白底牌 + 红字"（`stack > 1` 重叠态，牌是 0.66C），龙骨**整格跳过**。
- **v2.3 补充：龙骨压在座舱盖上的那一段会被削弱，这是对的，不要去"修"。** 座舱盖已经是 L\* 69~74 的浅色，同一 α 叠上去只剩局部 ΔL\* **7.0 / 5.2 / 7.1**（abyss 三架），而压在机身上是 **11.0 / 6.0 / 12.6**。所以光带的"最强段"实际落在第 2 行，不在机头格。读起来是"光从座舱背后涌出" —— 符合真实飞机（座舱盖本身反光，脊背从它后面才开始）。**不要因此把龙骨改成从 row1 起画**，那会丢掉"一条贯通 4 格的脊"这个唯一的结构感。

- **这条靠断言守，不靠这段文字守。** 出图看不出来的错，只能由测试拦。断言规格（给工程）：

  ```js
  // 读记录型 ctx 里那一次 gradientRect，断言龙骨矩形的长边
  const long  = Math.max(r.w, r.h)
  const short = Math.min(r.w, r.h)
  const stack = cellStack(cells, head.row, head.col)
  assert(long  === approx(stack > 1 ? 3 * C : 4 * C))   // 贯通四格（重叠态合法降为三格）
  assert(short === approx(PK.keelW * C))                // 0.30C，顺带锁住宽度
  ```

  **两个坑，不写清会白烧一小时：**

  1. **不能只断言 `h ≈ 4C`。** `mapRect` 在 `k = 1 / 3` 时把局部 y 映射到屏幕 x，龙骨矩形的 w/h **互换** —— 只断言高度会让四个朝向里两个误红。误红比不红更糟：它会诱人把测试改松，于是守门员废掉。**用长边/短边断言，与旋转无关。**
  2. **`from = 1` 有一个合法例外**：`cellStack > 1`（多架机头重叠，画白底牌 + 红字）时，代码**故意**从 row1 起画，避免亮带穿过数字。所以断言不能无条件写 `4C`，必须 `stack > 1 ? 3C : 4C`。**不豁免这一态，重叠局一出现测试就红，然后有人会去"修"那个例外 —— 而那个例外是对的。**

  测试名建议就叫「龙骨必须贯通四格」。它和现有那批"出图看不出来的错"的守门员（4 向龙骨亮端、序号恒正立）是同一类：**文档管愿意看的人，断言管不看的人。**

**#6 机翼后掠线**
每侧 2 条，从机身侧边（col1|col2 分界）向翼尖走，行进中向后偏移 0.37C → 视觉后掠角 ≈ 8.4°。暗色，线宽 `max(1, 0.025C)`。
- 为什么暗线不亮线：亮线在机翼上会读成"这里有缝、是不是两架飞机"；暗的 1px 读成"蒙皮拼缝"（这条已由 30px 出图验收）。
- 为什么只偏 0.37C：翼行只有 1 格高，偏超过 0.6C 会贴到后缘，看起来像机翼被削掉一条（违反约束②）。

**#7 机头前缘三角**
贴在机头格**朝外那条边的内侧**中央：宽 5.8px、深 3.6px 的深色小三角，顶点朝外。
- **它是质感线索，不是方向线索**（v2.2 改正：v1/v2.1 写"最强的单点方向线索"，是错的）。工程实测在 30px 格上这个小三角只有 4.8×3.0px，一半被 1.8px 描边压掉，**单独摘出来看不见**。它的作用是"机头不是一刀切的平头"，让机头格在近看时像尖的 —— 属于"有没有打磨过"的那一层，不承担"朝哪边"。
- 尺寸红线：宽 ≤ 0.18C。再宽会碰到 0.62C 的序号保护区。
- 方向的三条真正通道见 §5.11：并集轮廓 / 龙骨渐变 / 序号。

**#8 翼尖灯**
两个 2px 亮点，在 col0 左缘、col4 右缘的弦长中点。作用是把翼展两端"钉住"，让 5 格宽不是含糊的矩形而是一条有端点的翼。在 30px 屏上只有 1.7px，正好在噪点线上 → 有下限 `max(1.6, 0.055C)`。
- **不用红/绿航行灯**（真飞机的左红右绿）：那正好占了语义色的两个位置，绝对禁止。

**#9 尾喷口**
机尾中格（row3,col2）后缘内侧：0.40C × 0.16C 深色圆角块 + 上方 1px 亮缝。读作"发动机喷口"，是尾部的句号，让机尾不像被截断。
- **棋盘内不画尾焰**（越界 = 违反约束①）。尾焰只允许出现在非棋盘场景：大厅水印、飞机棋子图标（`plane-icon.js` 的 `join` 模式）。那里可以有 0.25C 外溢，因为周围没有格子语义。

### 5.5 换朝向（4 向）

**整架飞机画在旋转过的局部坐标系里，只有序号反旋转。**

```js
ctx.save()
ctx.translate(bboxCenterX, bboxCenterY)
ctx.rotate(rot * Math.PI / 2)          // rot: 0/1/2/3
ctx.translate(-localW / 2, -localH / 2) // localW = 5C, localH = 4C
... 画 #1~#9，全部用局部格坐标 ...
ctx.restore()
// 序号单独画在屏幕坐标：位置 = 机头格中心的屏幕位置（不旋转）
```

| 层 | 跟随旋转 | 说明 |
|---|---|---|
| #1~#9 | ✔ | 龙骨亮端、后掠方向、前缘三角顶点自动正确 |
| **#10 机头序号** | **✘ 恒正立** | 序号是**文字**不是图形。转 90° 的数字要歪头看，与"权威通道"冲突。业界通用做法（棋子、地图标记一律不转文字） |

两点注意：
1. **90°/270° 时 bbox 变成 4C×5C**。局部坐标系不变（永远 5×4），只是投影时对调。`shapeOf()` 已有"归一化到左上角"的逻辑（`plane-icon.js:20`），直接复用拿 `rows/cols`。
2. **1px 线旋转 90° 后仍是 1px**（正交旋转不插值），清晰度无损。这也是为什么只用 90° 整数倍。

### 5.6 机头序号：权威通道的四条保护规则

1. **保护区**：机头格中心 `0.62C × 0.62C`（C=36 时 22.3px）内不得有任何其他绘制物。
2. **绘制顺序**：序号是这一格**最后一个**绘制元素。
3. **对比度 ≥ 7:1**（算得 **7.6 ~ 9.8**，九组全部通过；v2.2 换机头色后从原来的 11.0~19.5 降下来，因为机头不再发白，浅底变深、和近黑 ink 的差变小）。字色固定 `headInk`，**不得使用身份色**（避免"1 号机的数字看起来像 2 号机的颜色"）。
4. **不降级**：`cell ≥ 22px` 字号恒 `0.52C`；`cell < 22px` **不是缩小而是换圆点**（§6.4）。8~11px 的数字会糊成一团，既不可读又难看，比"没有数字"更糟。

### 5.7 我方 vs 敌方：敌方**不画飞机**

> **敌方的 9×9 盘上永远不出现飞机的任何形状、剪影、幽灵轮廓、虚影、水印。**
> 敌方盘只有三种格：命中（橙爆点）/ 击毁（红叉）/ 未命中（灰点）。

理由（规则问题，不是美术问题）：
- 飞机是**隐藏信息**。任何"轮廓暗示"都在泄漏"这一带可能有飞机"，而机头位置决定整架生死 —— 泄漏一格 = 泄漏一条命。
- 击毁时也**不揭示**那架的 10 格。现状 `kill` 只画机头一格红叉，这是对的：揭示 10 格会让玩家通过"机型形状 + 朝向"反推布局习惯，形成不对称优势。

于是"我方 vs 敌方两套视觉语言"用**盘的层面**区分：

| | 我方海域 | 敌方海域 |
|---|---|---|
| 角色 | **战损报表**（我被打成什么样） | **扫描靶面**（我扫过哪里） |
| 底板 | `plate` | `plate` 再压暗 6%（混黑），`frame` 降一档 |
| 扫掠 | 放大且等待态时开 | 同左 |
| 信息密度 | 有身份色的飞机 = 高 | 只有点/叉 = 低，靠"更暗"把视觉重量让给我方盘 |

现状两块盘长得完全一样（见 `5-battle-390x844.png`），而任务完全不同。**压暗 6% 是这套区分里最便宜、最有效的一手。**

### 5.8 损伤表达：让描边当血条

现状"每格一个橙爆点"，**看不出这架还剩多少**（10 格里有 4 格是橙时尤其）。

做法：把 #2 亮描边的色值按损伤比例往 `danger` 混：

```js
const dmg = hitCellsInThisPlane / 10            // 0~1
const t   = Math.min(1, dmg * 2.2)              // 打到 45% 时最强
outline = mix(planeArt.keyline, danger, t)      // 透明度 0.42 + 0.10t
```

- 成本：**0 次额外调用**（只换 strokeStyle）。
- 效果：整架飞机轮廓从"冷白"渐变到"危险粉"，一座随形的血条。扫一眼轮廓颜色就知道"这架快没了"。
- 上限：`t ≤ 1`，透明度上限 0.52。再高会盖过机头序号。
- 只在我方盘 / 布阵页（飞机整体可见）适用。

> **⚠️ 当前状态：未接线，实测恒为 0（工程记为 PR-5）。**
> `battle.myCells()` 把命中格的状态覆盖成 `hit` / `kill`，飞机在那几格**不存在**，所以 `hitCellsInThisPlane` 永远数出 0，`t` 恒为 0，描边永远是冷白。
> 更要紧的连带后果：受损飞机现在是**带洞的轮廓**（10 格少掉几格，并集轮廓会绕着洞走）。验收时要专门看一眼那个洞 —— 读成"被炸开一块"才算对；读成"缺了块贴图"就得在 PR-5 里补一个"洞边加一圈 `planeArt.shadow`"的处理。**这一条不要当作已生效来验收。**

### 5.11 「层级」：三档线，以及各自该画在哪（v2.2 新增，v2.3 更正归因）

> **这一节保留下来的是一条分类规则，不是一条实现批注。** 一架飞机只允许有三档"线"：结构线（并集轮廓，2 条 stroke）、格缝（**它不属于飞机，不该有任何视觉重量**）、装饰线（全部弱于结构线）。
> "十张圆角卡片拼成十字"的成因在**填充层**，不在描边层（见下 P0）。但错的类型是同一个：**某样东西被按格处理了，而它属于整架。**

**三档线，按"重量"从重到轻：**

| 档 | 是什么 | 数量 | 线宽 / 做法 | 画在哪 |
|---|---|---|---|---|
| **① 结构线** | 整架的**并集轮廓** | 每架 **2 条 stroke**（同一条路径） | 暗 `0.05C`（C=36 → 1.8px）`rgba(2,8,16,0.55)` + 亮 `0.028C`（1.0px，下限 1px）`rgba(224,236,246,0.55)` | 只描并集路径的外边，**格内一律不描边** |
| **② 格缝** | 格子与格子的分界，**它不属于飞机** | 0 | 靠底色之间的 `inset` 露出来，不描边 | 只在结构线内侧，纯比例 `0.03C` |
| **③ 装饰线** | 龙骨 / 后掠线 / 翼尖灯 / 喷口 | 见 §5.3 | 全部弱于结构线 | 全部关在并集轮廓里面 |

**真正的根因（v2.3 更正：我 v2.2 写的三条 P0 归因全错，代码核对后推翻）**

v2.2 我判的是「描边打在每格上 / 龙骨按格画 / 后掠线按格画」。工程逐行核代码后推翻：`planeEdge()`（`board.js:363-379`）一直是**并集路径**（四个 `if (!has[...])`）；龙骨 `board.js:489` 是 `mapRect(f, …, from, …, 4)`，**跨 row0→row4 的一个连续矩形**；后掠线 `board.js:500` 的 `segPath` 从 col0 跨到翼尖，**一条线走完整个翼展**。三层都是对的。

**根因只有一层，在底色：`board.js:453-467`，8 个机体格是各自四条边都内缩 0.03C 的圆角矩形（圆角 0.10C）。**

相邻两格各缩 0.03C → **缝宽 0.06C，36px 格上是 2.16px**。这个数字是全部问题的钥匙：

| 事实 | 数（C=36） |
|---|---|
| 假缝宽度 | **2.16px**（0.06C） |
| 真轮廓的暗描边 | **1.8px**（0.05C） |
| 真轮廓的亮描边 | **1.0px**（0.028C） |

> **这张表本身就是"重复数据会漂移"的现场证据。** 同一组线宽在 §5.3 #1/#2、§5.4、§5.11 ①、这张表、§9 的 `PLANE_ART` 注释里一共写了 5 处。v2.3 我只改对了 3 处，这张表里的亮描边还留着上一版算错的 **1.2px**（正确值 1.0px，0.028C×36=1.008）—— 改完 §5.11 ① 就以为改完了。**5 处副本、改 3 处、漏 2 处，漏的那处恰好是"拿来做对比证据"的那张表。** 权威值只有 §5.3 #1/#2 一处，其余都是引用；引用处不该重算，只该抄或只该指向。

**假缝比真轮廓的暗线还宽。** 所以眼睛读成"每条线一样重"，不是观感问题，是尺寸问题。三个症状全部由这一层生成：

- 底色缝露出暗底板 → 看起来像"内部凭空多出 12 条边"
- 龙骨尾端 α 只有 0.021（几乎全透明），在那些极淡区段上暗缝透出来 → 看起来像"断成 3 段"
- 后掠线本身连续，但两侧的暗缝让它每格读成一段 → 看起来像"每格两道斜纹"

**三层症状，一个根因。**

**修法一句话：内缩与圆角是「轮廓」的属性，不是「格子」的属性。**

只对**整架 10 格并集的外边界**内缩 0.03C、圆角 0.10C；**10 格集合内部的任何边都不内缩、不圆角**。`planeEdge()` 已经在枚举"邻居不在集合内的边"，把内缩的作用对象从"每格的四条边"改成"每条外边界边"即可，圆角同理落在并集轮廓的 8 个外角上。

> **必查一条：机身 ↔ 机头那道缝。**
> 机头格是**独立的一次 fill**（颜色不同），如果它仍按自己那四条边内缩，机身与机头之间会留一条 2.16px 的暗缝 —— 那正是"白牌贴在飞机上"的**机械原因**。这条缝不除，新的 `head` 色救不回 36px 的观感：色值只解决了"白不白"，缝解决"是不是同一个物体"。验收时必须单独确认机头格与相邻机身格之间**没有**暗缝、两色直接接壤。

**不要同时动 `keelTail`（0.021 保留），理由是算出来的。**

底色焊死之后，龙骨在连续机身色上的合成结果（abyss 1 号机 body `#4789d4`，glow `#E0ECF6`）：

| 沿龙骨位置 | α | 合成色 | 对机身 ΔL\* | RGB 分差 |
|---|---|---|---|---|
| 机头端 u=0 | 0.300 | `#75a7de` | **11.0** | 46,30,10 |
| u=0.25 | 0.230 | `#6aa0dc` | 8.4 | 35,23,8 |
| u=0.50 | 0.161 | `#6099d9` | 5.8 | 25,16,5 |
| u=0.75 | 0.091 | `#5592d7` | 3.3 | 14,9,3 |
| u=0.88 | 0.056 | `#508fd6` | 2.2 | 9,6,2 |
| 机尾端 u=1 | 0.021 | `#4a8bd5` | **0.7** | 3,2,1 |

判据两条，都过：

1. **没有台阶。** 最大单步是每 1/8 长度（18px）跳 **1.4 级 L\***，远低于 banding 需要的 3 级。单调平滑 → 眼睛读成渐变，不读成色阶。
2. **在边缘归零。** 尾端 ΔL\* 0.7、RGB 分差 3/2/1 —— 是"淡到没有"，不是"到某处被切断"。**淡出（fade to zero）读作连续，切断（cut）才读作断。** 之前的"断成 3 段"是缝在中间挖洞，不是衰减值的问题。

所以结论：**keep 0.021，不动。**

> **唯一要预告的不对称：亮机身吃不住高光。**
> 2 号机（body L\* 70.1）龙骨机头端只有 **ΔL\* 6.0**，mono 1 号（L\* 70.4）**6.9**，到 u=0.75 就掉到 1.7~2.1。这两条龙骨会读成"机头附近的短亮楔"，而不是全长脊。**这和机头底色只能提 Δ4.1 是同一个物理**：机身已经接近高光色（`#E0ECF6`）的亮度，任何叠加都只剩很小余量。这是肤色本身的物理上限，不是衰减值的错 —— **调 0.021 只会把已经看不见的尾端抬到"略看不见"**。补偿在别处：这两架的序号对比是全皮肤最高的（9.3 / 9.8）。

**P1 `inset` 是纯比例，不设绝对上限（v2.3 第二次更正）**

```js
ins = Math.max(0.5, C * 0.03)      // 纯比例 + 亚像素下限，没有上限
```

v2.2 我写过 `min(cell*0.03, 2.2px)`，**上限是错的**，而且我给的理由也是错的：

- **上限错在破坏比例**。真机 C=36 → 1.08px，C=30 → 0.90px，lab C=90 → 2.70px，三者都恰好 3%。加上 2.2px 封顶后 lab 变成 2.44%，lab 图就不再模拟真机的观感 —— 而 lab 图的**唯一用途**就是在放大条件下预演真机。
- **理由错在单位**。我写「`cell*0.03` 在 C=90 时是 5.4px」，5.4px 其实是**缝宽**（两侧各缩 0.03C → 缝 = 0.06C），不是 `ins`。但这个混淆恰好暴露了真问题：**缝宽 0.06C 恒大于暗描边 0.05C**，比例 1.2，**与尺寸无关** —— 所以它本来就只能靠改比例来调，不可能靠加一个绝对上限来调。

- **下限 `0.5px` 保留，而且它和上限不对称**：下限有生理学依据 —— 亚像素会被抗锯齿吞掉，0.5 CSS px 是任何 dpr 下还留得住的最后一档；上限没有任何对应的物理依据，只有一个比例关系，而比例关系就该用比例表达。

> 顺带把定位说清：`inset` 现在的**唯一职责**是"让飞机别贴着格线"，不是"画一条缝"—— 缝已经由并集填充消灭了。所以它只需随尺寸线性缩放，不需要任何美学上限。

> **留档：v2.2 那三条 P0 的归因错误为什么值得记下来。**
> 错的方式是同一个 —— 我猜"某样东西被按格处理了，而它应该按整架处理"，方向是对的；但我把三个**已经正确**的层（描边 / 龙骨 / 后掠线）点成了嫌疑，真正的犯人是第四个（底色内缩）。这是只读规格、从"应该怎样"反推"实际怎样"的必然盲区。**规格作者的自查打不穿自己写的规格，只有量测能打穿。**

**方向到底靠哪几条通道（把职责写死，免得下次又让某个装饰去背方向）**

| 通道 | 强度 | 在哪个 LOD 档有效 |
|---|---|---|
| ① 并集轮廓（机头唯一 1 格宽前伸，翼 5 格、尾 3 格） | **最强** | 全部（<14px 无描边时靠剪影本身） |
| ② 龙骨渐变（亮端恒在机头） | 强 | C ≥ 22px（细节层） |
| ③ 机头序号 1/2/3 | **权威** | C ≥ 22px |
| ④ 机头底色（座舱盖） | 弱（ΔL\* 4~26，见 §5.4） | C ≥ 22px |
| ⑤ `headInk` 圆点 | 中 | C < 22px |

每一档至少要有两条通道同时在线，这是硬性要求。**机头前缘三角不在这个表里** —— 它是质感线索（§5.4 #7）。

### 6.1 每帧绘制调用基线

### 6.2 预算表

> **缓存单元的边界由 L2 扫掠决定（v2.1 更正）**：底板在 L1、格线在 L3，中间夹着 L2 扫掠 —— 所以 L1 和 L3 不能合进同一张位图，合了扫掠就无处可插。
> 可缓存单元只能是 **L3–L7**（格线 + 微点 + 刻度 + 飞机 + 命中标记）。L1 只有 4 次调用，本来也不值得缓存。
> **L8 叠加层不进缓存**：拖拽时 select/ghost 每帧都在变，进了缓存 = 每帧重建整张位图，比不缓存更差。

| 元素 | 静态 / 动态 | 缓存键（什么变化时失效） | 每帧增量 |
|---|---|---|---|
| 页面背景渐变 | 静态 | `(W, H, skin)` | 0（现算 1） |
| 背景网格 `bgGrid` | 静态 | `(W, H, skin)` | 0（现算 1） |
| 底板 + 外框 + 投影（L1，**不缓存**） | 静态 | `(size, skin, dpr, variant)` | 0（4） |
| 网格线（L3） | 静态 | `(size, skin, variant)` | 0（20） |
| 双轴刻度（L5） | 静态 | `(size, skin, variant)` | 0（18） |
| 空格微点（L4） | 静态 | `(size, emptySet, skin, variant)` | 0（1） |
| **扫掠核心扇段** | **动态** | — | **+1** |
| **扫掠拖尾 7 段** | **动态** | — | **+7** |
| **前沿线 + 束头** | **动态** | — | **+2** |
| 飞机 10 格 + 装饰 | 静态 | `(planesSet, skin, dmgMap, variant)` | 0（新版 13~15，替代旧 11） |
| 机头序号 | 静态 | 同上 | 0（1） |
| 命中 / 未命中 / 击毁 | 静态 | `(incoming, skin, variant)` | 0（≤3/格） |
| 叠加层 select / ghost（L8，**不进缓存**） | 半动态 | `(marks, dragCell)` | 0；拖拽中 +6~8 |
| 倒计时 / 出手数 | 动态（1Hz） | 字符串本身 | 0（恒定 2~3） |
| 皮肤切换 | — | 换 skin = **全部缓存失效一次** | 一次性重绘 |

**结论：真正"每帧必变"的只有扫掠（+10）和几个数字（+1）。** 其余都是"状态变了才需要重画"。

### 6.4 LOD 降级闸门

> **总原则（v2.1 新增，防止误读）：LOD 只降「读数」与「细节」，永降「结构」。**
> 结构 = 底板 / 外框 / **格线** / 两层底色。这些在任何尺寸下都必须画，因为它们定义"这是一张 9×9 的盘"。
> 读数 = 刻度 / 空格微点 / 机头序号。细节 = 龙骨 / 后掠线 / 翼尖灯 / 喷口 / 投影。
> **机头底色（座舱盖）算"半读数"**：它存在的理由之一就是给序号当浅底（§5.4），序号一关它就跟着关，改由 `headInk` 圆点接管方向。它不是细节，不能按"细节预算不够先砍"来处理。

| 格子 C | 保留（结构 + 读数 + 细节） | 关闭 |
|---|---|---|
| **≥ 30px**（390 屏大棋盘 36px） | 全部：10 层 + 序号 + 刻度 + 微点 + 扫掠 | — |
| 22 ~ 30px（320 屏大棋盘 30px） | 全部（线宽取 `max(1, 比值)` 下限） | — |
| **14 ~ 22px** | 结构全部（含**格线**）+ 双层描边 + **机头圆点** | 细节全部（投影/后掠线/翼尖灯/喷口/龙骨）+ 读数全部（刻度/微点/序号）+ **扫掠** + **机头底色**（§5.4） |
| **< 14px**（缩略盘 11px） | **底板 + 外框 + 格线** + **1 次底色填充**（机体，机头同色）+ 机头圆点（靠并集剪影 + 圆点表方向） | 其余全部，含描边与机头底色 |

**`<14px` 那行必须保留格线。** v2 字面写的"仅 2 次底色填充 / 其余全部关闭"是起草错误：11px 的格子去掉格线，10 格的飞机就散成两三个色块飘在底板上，"一架飞机占了几格"直接读不出来 —— 而缩略盘的唯一任务就是回答这个。现有 `board.js:235-239` 缩略盘本来就在画格线，不是新开销（合批后 1 次 stroke）。

挂靠现有常量：已有 `AXIS_MIN_CELL = 22`（刻度/微点）。新增 `SWEEP_MIN_CELL = 22`、`DETAIL_MIN_CELL = 22`、`DECOR_MIN_CELL = 14`、**`HEAD_PLATE_MIN_CELL = 22`**。

四个 22 只是**同值，不是同一个常量**。理由各不相同：刻度/微点/扫掠是「读不了就没意义」，机头底色是「序号没了，浅底就没存在理由」。**故意不复用 `AXIS_MIN_CELL`** —— 复用会让将来调刻度阈值时机头底色静默跟着动，且代码上看不出牵连。每个常量旁写一句自己的理由。

### 6.5 真机自测（5 分钟）

1. `draw.js` 每个原语里累加一个模块级 `drawCount`。
2. 跑 10 秒，记录每帧 `drawCount` 与 `dt`，取 p95。
3. 判据：**p95 帧耗时 ≤ 8ms 且 p95 调用数 ≤ 300** → 60fps 稳。
4. 重点三台：iOS 老机型（iPhone 8）、安卓中端、安卓千元机。
5. 超了就按 §6.3 P1→P2→P3 降，**不要先砍拖尾层数**（8→6 会露出条带，视觉损失远大于省下的 2 次调用）。

> 判据不是「它在不在 `theme.js` 里」，是「**它画不画到屏上**」。我第一次数成 5 处引用、第二次数成 0 处，两次都是因为我 grep 的是 `.disabled` 而不是 `c.disabled` —— **同一个键，同一个坏模式，我连错两次**。所以查验方式一栏写的是「绘制引用」三个字：`z.disabled` 和 `c.disabled` 在字符串层面长得一样，只有语义能分开。

### 9.2 对契约的四点补充说明

1. **`trail` 必须是 7，不能停在 4**（v2.4 从 8 改 7）。4 层 → 相邻 Δα 0.0336（8.6/255）会看出切面；7 层 → 阶梯头两格 0.090/0.072，最大差 0.018（4.6/255），安全。原来写 8 是错的：第 8 层 α=0.001 ≈ 0.26/255 低于 8bit 量子，永远画不出来。每层只是一次 `fill`，7 层在一帧 158 次的总量里占 4%。现在它被收进全局 `SWEEP`，皮肤改不动 —— 所以这个数字定了就不会被某个皮肤悄悄改坏。
2. **`arc` 与拖尾是两件事**：`SWEEP.arc = 40` 是**硬边核心**张角，拖尾在它之外再外扩 `trail × seg`，总跨度 = `arc + trail × seg` = **75°**。别把 `arc` 当总跨度用，也别给总跨度另立一个常数 —— v2.4 之前它是个独立数字，于是它漂到了 80°（= 按 8 层算的），而代码一直画 75°。
3. **`miss` / `missRing` 请求进契约**（可选，已在 §9 的皮肤块里给了值）。它不是语义三色，是"无信息"的中性标记，但 `mono` 需要更亮的一版（`#4C7093` 在 abyss 是 3.35，够用；在 `mono` 的 `#0C1014` 上也是 3.35，但 `mono` 整屏更亮，需要 `#7D8B99`）。不加也能跑，不是最优。
4. **`PLACEHOLDER` 四个键为什么单独立一层**（v2.4 新增）。它们原本是 v1 的遗留键，规格 §9.1 当时的写法是「未进契约；非棋盘场景暂保留」——**「暂保留」是个无限期的许可证**，于是它们停在第三种状态：声明着、但没登记。整理时有三条路（删 / 从 `palette[0]` 派生 / 立成一层），选第三条，理由是前两条都在掩盖一个真事实：**「没有身份」和「没有皮肤」是两种真实存在的显示态**，它们不随皮肤变。删掉会让老画法通道裸奔；从 `palette[0]` 派生则会让「没有皮肤」长得像「第 1 架」，那是把缺失伪装成一种选择。

> **顺带一条检查的事，比这四个键本身重要。**
> `planeOffHead = #2A4A66` 与 `abyss.frame` / `abyss.borderHi` **同值**。所以「每个色值都在规格里登记过」这条按值检查会放它过关 —— 而它一次都没被登记为"槽位关闭态"。等 `dusk` 落地（`frame = #8A6A45`），这个键就会带着一个属于 `abyss` 的值留在代码里，绿着出去。
> **按值登记只能证明"这个颜色出现过"，不能证明"这个键有意义"。** 所以 `check-skin-tokens.js` 除了按值查，还必须按**键名**查：`theme.color` 下的每一个键，在 §9 的某个块里得有它自己的位置。值撞上了不算数 —— 同值不等于同义。

另外回应工程问的两件事：

- **「减少动态效果」开关要接，但它接的是 `masterAlpha`，不是性能降级。** 这是两件事：前者是**无障碍**（信息零损失，因为扫掠不承载信息），后者是**性能**（若给玩家开关，等于把"手机行不行"的判断外包给不懂的用户）。两个开关不合并、不互相代替。
- **敌我两盘配色不同**（§5.7 敌盘压暗 6%、外框降一档），所以任何缓存键都要带 `variant: 'mine' | 'foe'`。

### 9.3 已知缺口（带编号，不是"暂保留"）

**「已知缺口」和「暂保留」的区别**：前三者有编号、有归属、写清为什么现在不做；后者是一张无限期许可证 —— `planeOffHead` 就是上一张许可证放出来的东西，它在"暂保留"里躺了三个版本，最后靠撞值蒙过了检查。

| 编号 | 缺口 | 现在怎么处理 | 什么时候收 |
|---|---|---|---|
| **G1** | **rgba 从未参与逐值比对。** `theme.js` 有 22 个 rgba 字面量槽位，断言一一个都没查；实测其中 12 个在本规格里查不到 | 脚本每行打印「48 个 hex 槽位参与逐值比对；另有 22 个 rgba 未参与」，**把盲区写进输出**，不假装验过 | **PR-5**。收法：规格把 rgba 改写成「色 + alpha」两段（`sweepColor` + `edge: 0.20`，而不是 `rgba(191,243,255,0.20)`）；`planeArt.keelTail` / `lightDim` 是算出来的派生值，要写公式而不是写值。**现在硬纳会误报**，误报比不报更坏 —— 它会诱人把检查改松 |
| **G2** | `STATE` 里有 5 个是「语义色 / 主色 + alpha」的派生值（`conflict`=`danger@.30`、`ghostBadLine`=`danger@.88`、`ghostOk`=`primary@.40`、`dragOrigin`=`primary@.14`，`ghostBad` 同 `conflict`），现在以**字面量**登记 | 字面量登记，逐值比对能过 | **PR-5**，与 G1 同一批收：需要 `at(color, alpha)` 这种参数化派生，且要改 5 处调用点的表达方式。收益真实（`danger` 改了它们会不跟）但不紧急，而"先登记字面量"至少让它们从**未登记**变成**已登记** |

> **原本还有 G3（`disabled` 名字与语义不符，建议改名 `cellSpent`），已撤。** 复核发现它 0 处绘制引用 —— 它不是"名字错"，是"不存在"。名不副实的前提是它得存在。这条撤掉本身是个提醒：**缺口清单也会写错，写的时候要标清依据是「声明」还是「绘制」。**

## 附 B. 无 clip 的扇形多边形（可直接用）

思路：射线从中心出发，与**棋盘正方形**求交。距离 `d(θ) = half / max(|cosθ|, |sinθ|)`，在轴上是 `half`、在角上是 `half×√2`。扇段跨度 ≤ 40° < 90°，所以最多跨一个角点，把那个角点插进路径即可沿边界走，而不会切角。

```js
const HALF_PI = Math.PI / 2
const CORNERS = [Math.PI / 4, 3 * Math.PI / 4, 5 * Math.PI / 4, 7 * Math.PI / 4]

/** 相对棋盘中心的边界点 */
function edgePoint(half, a) {
  const c = Math.cos(a), s = Math.sin(a)
  const d = half / Math.max(Math.abs(c), Math.abs(s))
  return { x: c * d, y: s * d }
}

/**
 * 构造一个「被正方形截断的扇形」路径。
 * @param {number} a0,a1 弧度，要求 a1 > a0 且 a1 - a0 <= HALF_PI/2
 */
function wedgePath(ctx, cx, cy, half, a0, a1) {
  ctx.beginPath()
  ctx.moveTo(cx, cy)
  let p = edgePoint(half, a0); ctx.lineTo(cx + p.x, cy + p.y)
  for (let i = 0; i < 4; i++) {
    if (CORNERS[i] > a0 && CORNERS[i] < a1) {
      const q = edgePoint(half, CORNERS[i])
      ctx.lineTo(cx + q.x, cy + q.y)
    }
  }
  p = edgePoint(half, a1); ctx.lineTo(cx + p.x, cy + p.y)
  ctx.closePath()
}
```

验证要点（建议工程写一个临时脚本跑一遍）：

- `edgePoint(half, π/4)` 必须正好等于 `(half, half)`（角点）。实测成立：`d = half/0.7071 = half×1.4142`，乘 `cos=sin=0.7071` 恰好是 `half`。
- 相邻扇段（如 `[a-10°, a-5°]` 与 `[a-5°, a]`）在第 2 个角度的 `edgePoint` 完全相同 → 无缝隙、无重叠。
- 角度跨过 0°/360° 时用未归一化的弧度直接算（`a - CORE` 可以是负数），`cos/sin` 天然循环，不需要取模。

`edgeLine` / `headTick` 的边界点同理用 `edgePoint(half, a)`。
