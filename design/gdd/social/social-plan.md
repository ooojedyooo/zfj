## 0. 一页速览（给拍板的人）

**一句话结论：** "约好友打一局"这个闭环，微信小游戏**现在就能做通**，而且几乎不用新后端——
把已有的建房、分享 query、房间云函数、表情动作串起来即可；真正做不到的不是技术，是
"微信不给普通小游戏系统级好友列表"和"文字聊天要过内容安全"这两件事，需要换落地方式。

### 三个关键裁决（需要你点头）

| 裁决 | 我们怎么做 | 为什么 |
|---|---|---|
| **裁决一：没有"好友列表"这回事，用"转发邀请"代替** | 不做独立好友列表。产品里叫"邀请好友"，本质是生成邀请卡转发给微信好友/群，对方点开就进房 | 微信小游戏不向普通小游戏开放玩家微信好友关系链（开放数据域能力边界**需技术核实**）。硬做好友列表=做一个玩家自己维护的通讯录，没人会用 |
| **裁决二："简单聊天"先用表情顶，文字聊天放二期** | MVP 上快捷表情（云函数已有 `emote` 动作，几乎零成本）；文字聊天放二期，且必须先接内容安全 | UGC 文字是内容安全硬门槛，不接审核就上=审核不过/下架风险。表情是预设的，没有 UGC 风险，还更贴合"打一局"的轻量节奏 |
| **裁决三：MVP 只保闭环，传播和生态往后放** | MVP 三件：邀请卡带房间信息 / 好友点卡自动进房 / 表情互动。战报卡、排行榜、观战、奖励全部后置 | 先把"能不能约到人打完一局"验证跑通，再谈留存和拉新。MVP 多做一件就多一个审核面和故障点 |

> **补充裁决（v1.1 · 用户 2026-11-24 拍板）：房间密码——好友私密可选，自动匹配不用密码。**
> ① 好友约战：房主开房时可**可选**设 4 位密码，邀请卡带房间号 + 密码，好友点卡自动回填并进房；
> ② 自动匹配：只进公开房，**不带也不校验密码**；
> ③ 明确不做"邀请房默认密码 / 中途 setPassword 改密"，相关遗留待办就此取消（详见 §2.5）。
> 本条已由主理人代码核实，两条路径天然分离，**不是技术核实悬挂项、不需要改任何代码**。

### 铁律 remind（贯穿全篇）

- **T-08：不揭示对方飞机形状。** `games` 集合客户端不可读写，只有云函数能碰。
  任何社交功能若让一方看到另一方布阵/剩余飞机位置，即为破坏 T-08，一票否决。
- 本盘点所有社交功能**均不改对战数值**，因此不引入主导策略或经济失衡；
  唯一的经济风险点是"邀请奖励"（第 3.6 节），若引入虚拟激励须另立经济设计，届时补 GDD。

## 1. 现状锚点（我采信的事实，不重新发明）

以下是主理人已核实的项目现状，作为本盘点的地基，不再验证、不再扩展：

| 已有能力 | 位置 / 说明 | 对社交的意义 |
|---|---|---|
| 建房 / 快速匹配 | 房名、架数(1~3)、限时、公开/私密；已有 1/2/3 架快速匹配 | "约好友"的容器已经现成，缺的只是"把房间带给好友" |
| 分享骨架 | `core/share.js`：被动分享 + 主动分享 + query 传参；battle/lobby/result 已挂 `onShare` | 邀请卡的底座已铺好，**但 query 现在没带房间邀请信息**——这是 MVP 要补的关键缺口 |
| 房间云函数 | `room`：create / join / match / list / search / get / leave（已写，未上传） | 好友点卡进房靠 `join`/`get`，无需新后端 |
| 对局云函数 | `game`：deploy / fire / emote / surrender / tick / sync（已写，未上传） | `emote` 已存在 → 表情互动几乎零新增成本 |
| 最近对手 | `rivals.js`，本地记录 | "再战一局"的现成数据来源 |
| 昵称 / 皮肤 / 音效 | `profile.js`（昵称）/ `skin.js`（本地皮肤）/ `audio.js`（程序化音效） | 昵称是 UGC，排行榜/战报卡展示时要注意内容安全（见 §7 核实点 5） |
| 玩法核心 | 9×9 棋盘，1~3 架飞机，机头击中=击毁，回合制 | 每局结论清晰（击落数/用弹数），天然适合做战报 |

## 2. 你提的 4 件事，逐条拆解（§2.5 为 v1.1 补充裁决）

每条按「你想要的体验 → 微信小游戏能做到什么程度 → 限制在哪 → 裁决」四段写。
裁决即结论，不含"待确认"悬挂项；平台边界不确定处标「需技术核实」并给默认方案。

### 2.1 约好友开局

- **你想要的体验：** 约一个现实里的朋友，两人进同一局，各藏各的飞机，互相打。
- **能做到什么程度：** **完全能做到。** 建房、房间号、快速匹配都已存在，只差"把房间号/邀请带到好友手上，好友一键进房"这最后一环。补上即闭环。
- **限制在哪：** 微信小游戏不能主动给离线好友推一条"邀请通知"（没有 App 那种推送唤醒）。好友必须在微信会话里**点开你发的卡片**才能进来。这是平台现实，不是缺陷。
- **裁决：** MVP 用「你发邀请卡（带房间号）→ 转发给好友/群 → 好友点开自动进房」落地。产品语言叫"邀请好友"，别叫"发送通知"。

### 2.2 跟好友简单聊天

- **你想要的体验：** 对战时跟好友说句话，比如"来啊""你完了"，增加互动感。
- **能做到什么程度：**
  - **文字聊天：能做，但重。** 要自建消息通道（云函数 + 数据库），且 UGC 文本**必须接微信内容安全**（`msgSecCheck` 云调用）+ 敏感词 + 举报，否则审核与风控过不去。
  - **表情聊天：能做，且极轻。** 云函数 `emote` 动作已存在，客户端加一排预设表情按钮即可，没有 UGC 内容风险。
- **限制在哪：** 内容安全是硬门槛（文字）；小游戏里弹系统键盘做输入，体验也偏重，打断对战节奏。
- **裁决：** MVP 用**预设表情**顶替"简单聊天"，把情绪互动做到位；**文字聊天放二期**，且以"内容安全接入完成"为上线前置条件，做不到就不上（见 §7 核实点 4）。

### 2.3 好友列表

- **你想要的体验：** 一个"我的好友"列表，能看到谁在玩，点一下就邀请。
- **能做到什么程度：** 微信小游戏**不向普通小游戏开放玩家的微信好友列表**。能落地的是两种替代：
  1. **最近对手 / 常玩的人**列表（`rivals.js` 已有基础）——本地记录，点一下"再来一局"；
  2. 靠**转发**承载"好友"概念——好友关系存在于微信会话里，不必在游戏里再复制一份。
- **限制在哪：** 开放数据域 / 关系链到底开放到什么程度，**需技术核实**（见 §7 核实点 1）。但即便有部分能力，也不足以支撑一个"微信好友列表"式的功能。
- **裁决：** **不做独立好友列表。** MVP 用"转发邀请 + 最近对手"覆盖绝大多数场景。真好友列表放**观察期**，仅在技术核实给出明确可用能力且数据证明有需求时才重新评估。

### 2.4 给好友发送房间游戏请求

- **你想要的体验：** 像"发起游戏邀请"一样，点一下把"来我这局"的请求推给某个好友，对方点一下就进。
- **能做到什么程度：** 在微信小游戏里，这个"请求"的**真实形态就是一张分享卡片**：你分享带房间号的卡给好友/群，好友点开进房。功能效果等价于"游戏邀请"，只是承载物是卡片而非系统通知。
- **限制在哪：** 不能主动推送给离线好友、不能唤醒对方；接受方必须主动点卡片，且卡片只在有效期内有用（房间过期/满员要降级处理）。
- **裁决：** MVP 用「邀请卡 = 游戏请求」落地。把产品语言统一成"邀请好友"，避免让玩家期待"推送通知"那种不会出现的行为。

> **一句话合并 2.1 与 2.4：** 对微信小游戏来说，"约好友"和"发房间请求"是同一件事的两面——
> 就是**发一张带房间号的邀请卡，好友点开进房**。一条实现覆盖两个需求。

### 2.5 房间密码规则（v1.1 补充裁决 · 用户 2026-11-24 拍板）

> 这是对 §2.1「约好友开局」与"自动匹配"路径的边界裁决。用户已拍板、主理人已代码核实，
> 两条路径天然分离，**无需改代码，也不是技术核实悬挂项**。

- **① 好友约战 = 房主可选设密码 + 邀请卡带房间号和密码：** 房主开房时可打开「私密」开关设 4 位密码，
  密码是**可选的**（想公开也行，不强制）；邀请卡 `share.roomQuery(roomNo, pwd)` 把房间号与密码一起带出去，
  好友点卡自动回填 → `joinRoom({roomNo, password})` → 云端校验。
  → 设计含义：私密性由房主在开房时一次性决定，不额外增加"进房再输密码"的步骤，保住"点卡即进"的轻量体验。
- **② 自动匹配 = 只进公开房、不用密码：** 匹配池只捞公开房（`isPublic: true`），带密码的房根本不会被匹配到；
  匹配新建的房无密码（云端 `cloudfunctions/room/index.js` 的 `match` 用 `.where({isPublic: true, ...})`，
  离线版同样过滤掉带密码的房）。
  → 设计含义：陌生人匹配永远不接触密码概念，玩家不会被"要不要设密码"打断。
- **③ 明确不做"默认密码 / 中途改密"：** 不做"邀请房默认给一个密码"，也不做"开房后中途 setPassword 改密"。
  好友要私密就开房时自己设一次；自动匹配根本不碰密码。
  **此前记录的"下一期解禁云函数做 setPassword/update"遗留待办就此取消**，不再排期。
- **边缘情况（沿用既有降级口径，不新造流程）：**
  1. 邀请卡携带的密码不对 / 房间状态已变而卡未更新 → 按 §2.1 的进房失败口径处理：给出提示并降级到快速匹配；
  2. 房主给带密码房想走自动匹配 → 不会发生（匹配已按 `isPublic` 过滤），无需额外校验分支；
  3. 公开房被转发邀请卡 → 邀请卡 `pwd` 为空，好友点卡直接进房，行为与"无密码邀请"一致。
- **判据对齐：** 不改变对战数值（无主导策略 / 经济失衡），不触碰棋盘数据（不破坏 T-08）；
  邀请卡多带一个极短密码字段，仍落在 §7 核实点 2"只带极短参数"的既定口径内，**不新增技术核实项**。

## 3. 补充功能（你没想到的，7 条）

筛选原则：**贴合轻量对战、复用已有能力、克制**。没有大厂式好友动态、公会、语音房——那些对"打一局炸飞机"是负担。
每条给价值、为什么适合、四判据速览（详见 §6 汇总表）。

### 3.1 战报分享卡（二期）

- **价值：** 一局结束生成一张可晒的卡片——"我用 3 发击落了好友 2 架飞机"——转发到群/朋友圈，带来炫耀感、自然拉新和回流。
- **为什么适合炸飞机：** 每局结论极清晰（击落几架 / 用了几发 / 赢了没），数据现成；且复用 `share.js` 的被动/主动分享与结果页 `onShare`，几乎零额外后端。
- **判据：** 平台能做✓ / 不要云（数据本地已有）/ 审核风险低 / 不破坏 T-08（**硬约束：只晒自己战果与击落数，绝不展示对方布阵或剩余飞机位置**）。
- **成本 低：** 结果数据已有，加一张程序化绘制卡片 + 一句文案模板即可。

### 3.2 表情互动（MVP）

- **价值：** 对战中一键发个表情（挑眉、加油、得意），把"打一局"从纯点击变成有情绪的社交。它同时是"简单聊天"的轻量替代。
- **为什么适合炸飞机：** 回合制有天然的空档（等对方回合），正好发表情；云函数 `game.emote` 已存在，客户端加一排 Canvas 自绘按钮 + 短暂动画即可。
- **判据：** 平台能做✓ / 要云（动作已存在）/ 审核风险低（**预设表情，非 UGC**）/ 不破坏 T-08。
- **成本 低：** 后端零新增，客户端接线 + 程序化绘制（禁 emoji，沿用项目铁律）。

### 3.3 最近对手再战（二期）

- **价值：** 打完一局，结果页直接给"跟 TA 再来一局"按钮——把一次偶遇变成连续对战，是最省力的复玩钩子。
- **为什么适合炸飞机：** `rivals.js` 已有最近对手记录；"再战"= 拉起快速匹配或按上次架数重建房，都是现成能力。
- **判据：** 平台能做✓ / 要云（复用建房/匹配）/ 审核风险无 / 不破坏 T-08。
- **成本 低：** 加一个入口 + 复用建房流程。

### 3.4 轻量战绩沉淀「我的战绩」（二期）

- **价值：** 一个简单页面显示总局数、胜率、最佳战绩（如"最快 3 发通关"），给玩家留存目标，也为后续排行榜打数据底子。
- **为什么适合炸飞机：** 每局结果天然可结构化沉淀；默认走本地存储，无云依赖，体量与小游戏匹配。
- **判据：** 平台能做✓ / 不要云（**默认本地**；跨设备才需云，不列入本批）/ 审核风险无 / 不破坏 T-08。
- **成本 中：** 要新增对局结算写入、统计口径与持久化结构 + 一个战绩页 UI，比"加个按钮"重一档。

### 3.5 好友 / 全球排行榜（三期，含赛季制延伸）

- **价值：** 胜负有排名，"打败好友"多一层成就感；全球榜给长期目标。
- **为什么适合炸飞机：** 战绩数据二期已沉淀，排行榜是水到渠成的复用；赛季制是它的重形态（每季重置榜单），放观察期，不进前三期实现。
- **判据：** 平台能做（全球榜✓；**好友榜依赖关系链，需技术核实**）/ 要云（云端聚合排名）/ 审核风险中（**昵称是 UGC，展示需过滤，见 §7 核实点 5**）/ 不破坏 T-08。
- **成本 高：** 好友榜能力未定 + 云端聚合 + 昵称治理，链条长；赛季制另算更高成本。

### 3.6 邀请回流奖励（三期 / 观察）

- **价值：** 邀请好友并完成首局，双方得一点奖励（如皮肤碎片），用轻激励推动拉新。
- **为什么适合炸飞机：** 皮肤系统已存在，奖励可挂靠现成皮肤，不必新造虚拟经济。
- **判据：** 平台能做✓ / 要云（记录邀请关系 + 防刷）/ **审核风险中-高（微信对"诱导分享"敏感，分享与奖励不能强绑定）** / 不破坏 T-08。
- **成本 中：** 机制不复杂，但合规设计（不诱导、可无奖励正常玩）与防刷要花功夫。
- **裁决：** 放观察期，**不做"分享得奖励"的强诱导**；若做，只做"双方完成对局后各自获得"的弱奖励，且与"是否转发"解耦。若届时引入可交易虚拟物，须先补经济设计 GDD。

### 3.7 观战（观察期，倾向不做）

- **价值：** 好友对战时旁观学习 / 凑热闹，有观赏和社交价值。
- **为什么适合炸飞机（有限）：** 回合制让观战在技术节奏上可行；但对轻量小游戏，收益不明、成本很高。
- **判据：** 平台能做✓ / 要云（观战视角实时同步）/ 审核风险低 / **破坏 T-08 风险最高——观战者等于同时看到双方棋盘，必须做脱敏与延迟**。
- **成本 高：** 需要新的观战数据通道 + 严格的"只呈现已发生的开火结果、不呈现未公开的布阵"改造，架构改动大。
- **裁决：** **观察期，默认不做。** 除非未来有明确数据证明需求，且能在不违反 T-08 的前提下低成本实现（例如只回放已结束的战报），否则不列实现计划。

## 4. 分期路线图

### 4.1 分期逻辑

- **MVP（上线第一批）：** 只做能让"约好友打完一局"闭环跑起来、又不踩审核红线、不依赖好友关系链的功能。
- **二期（闭环验证后）：** 补留存与传播——战报、再战、战绩、文字聊天（合规先行）。
- **三期 / 观察：** 放大与生态——排行榜、邀请奖励、观战；以二期数据和技术核实结果为进入条件。

### 4.2 总表

> 成本为 低 / 中 / 高，理由见第 3 节各条；无互斥不设"代价"列。

| 功能 | 用户价值 | 实现成本（理由） | 平台 / 审核限制 | 建议期次 |
|---|---|---|---|---|
| **F1 邀请卡带房间信息**（发出+点开进房） | 约好友闭环的核心 | **中**：发出端复用 share 近零成本；接收端要改冷启动流程解析 query 并自动 join + 房间过期/满员降级 | 不能主动推送给离线好友；query 在群/会话冷启动是否完整保留**需技术核实** | **MVP** |
| **F2 表情互动** | 对战有情绪互动，顶替聊天 | **低**：`game.emote` 已有，客户端加按钮+动画 | 预设表情无 UGC 风险；动作是否已接线到 UI**需技术核实** | **MVP** |
| **F3 战报分享卡** | 炫耀、拉新、回流 | **低**：结果数据已有，复用 share + 一张程序化卡 | 只晒自己战果，禁展示对方布阵（T-08） | 二期 |
| **F4 最近对手再战** | 复玩钩子 | **低**：`rivals.js` 已有，复用建房/匹配 | 无 | 二期 |
| **F5 我的战绩** | 留存目标，为榜单打底 | **中**：新增结算写入、统计口径、持久化 + 战绩页 | 默认本地；跨设备需云（不列本批） | 二期 |
| **F6 文字聊天** | 你明确要的"简单聊天"完整版 | **高**：消息通道+输入UI+内容安全+敏感词+举报，全链条 | **UGC 文本必须过内容安全**，做不到就不上 | 二期（合规先行） |
| **F7 好友/排行榜**（赛季延伸观察） | 竞争与长期目标 | **高**：好友榜依赖未定的关系链 + 云聚合 + 昵称治理 | 好友榜可行性**需技术核实**；昵称 UGC 需过滤 | 三期 / 观察 |
| **F8 邀请回流奖励** | 拉新激励 | **中**：云端记邀请关系+防刷；奖励挂靠现有皮肤 | **诱导分享审核风险中-高**，需与转发解耦 | 三期 / 观察 |
| **F9 观战** | 观赏与陪伴 | **高**：新观战通道 + T-08 脱敏/延迟改造 | **与 T-08 根本冲突风险最高** | 观察期，倾向不做 |
| （不做）独立好友列表 | — | — | 平台不给普通小游戏好友关系链 | 不列入实现计划 |

### 4.3 MVP 边界（做什么、不做什么）

**做（三件，一个闭环）：**
1. 邀请卡带房间邀请信息（补 `share.js` 的 query 缺口）；
2. 好友点卡冷启动 → 解析 query → 自动加入对应房间（含过期/满员降级）；
3. 预设表情互动（复用 `game.emote`）。

**不做（及理由）：**
- 不做文字聊天——内容安全是硬门槛，MVP 不背这个审核面；
- 不做独立好友列表——平台不给能力，做了也没人用；
- 不做战报卡/战绩/排行榜/观战/奖励——MVP 只验闭环，传播与生态后置。

## 5. 最小可上线社交闭环（推荐路径）

**从点开游戏到跟好友打完一局，最短路径：**

1. **A 建房**：在大厅点"建房"，设人数/架数/限时（**已有能力**）。
2. **A 发邀请**：点"邀请好友"，走 `core/share.js` 主动分享，生成**带房间号 query 的卡片（房主若设了私密密码，邀请卡同时带密码）**，转发给微信好友或群（**复用已有 share，补 query 字段**）。
3. **B 点卡进房**：好友在会话点卡片 → 小游戏冷启动 → 解析 query 拿到房间号（**复用已有 query 传参**）→ 自动 `room.join` 进房（**复用已有云函数**；私密房由邀请卡自动回填密码）；房间过期/满员/密码不对则降级到快速匹配或给出提示。
4. **双方布阵开打**：`deploy` 布阵 → `battle` 回合开火（**已有玩法**）。
5. **情绪互动**：对战中任一方点快捷表情，走 `game.emote`（**已有云动作**）。
6. **决出胜负**：机头被击中=击毁，一局结束进结果页（**已有 scene，已挂 onShare**）。

**用到的已有能力：** 建房/快速匹配、`core/share.js` 分享与 query 传参、lobby/battle/result 的 `onShare`、
云函数 `room.join`/`room.get`、`game.emote`、`deploy`/`battle` 场景。
**不新增：** 好友关系链、文字聊天、任何新后端集合。

**一句话描述：**
> A 建房 → 发一张带房间号的邀请卡 → B 点卡自动进房 → 双方对战（可发表情）→ 决出胜负；
> 全程复用现有建房、分享 query、房间云函数和表情动作，不碰好友关系链、不做文字聊天。

## 8. 已知风险与取舍

- **平台现实：** 转发邀请依赖用户主动，不能主动唤醒好友——接受它，产品语言统一为"邀请好友"。
- **审核门槛：** 文字聊天（F6）与邀请奖励（F8）是审核敏感点，均以"合规先行"为上线条件，不达标就不上。
- **T-08 红线：** 战报卡只晒自己战果；观战（F9）因与 T-08 根本冲突，默认不做。
- **经济设计缺口：** 本期社交功能不引入虚拟经济；F8 若引入可交易激励，需另立经济 GDD 后再评。
- **范围纪律：** MVP 严格只做三件，多做一件就多一个审核面和故障点；传播与生态类功能一律后置。
