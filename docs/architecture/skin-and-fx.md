## 0. 结论速查

| 问题 | 结论 | 依据 |
|---|---|---|
| 重绘策略 | **继续全量重绘**；**不做脏矩形**；**离屏缓存降为 P5**（真机 p95 超标才做） | art 实测：新版 160 次（未合批）/ **122 次（合批后）**，60fps 预算内 6.1ms@p95；缓存是"备用手段"不是"当务之急" |
| 真正的性能抓手 | **网格线合批（−38/帧）+ 扫掠状态机（等待态才开，关时 0 次调用）** | 40 次独立 `stroke` 画 20 条线，是白送的；扫掠只在"对方回合"存在，`masterAlpha===0` 时整层跳过 |
| 图层栈 | **采用 art §4.5 的 L0–L10**：扫掠在**底板之上、格线之下** | 「语义色不被吞掉」靠**图层次序**保证，不靠调透明度 —— 这是唯一可靠的保证方式 |
| 扫描扇边界 | **射线-矩形求交（闭式解）替代 `ctx.clip`**，扇面多边形顶点直接落在格区四条边上 | 格区正方形**以扫掠圆心为中心** → 边界半径 `= h / max(|cosθ|,|sinθ|)`，三行代码精确求解，零 clip |
| 飞机朝向 | **几何旋转（点集走 90° 映射），不用 `ctx.rotate`** | 保住 `svg-ctx` 出图真实性；90° 整数倍旋转无插值，1px 线不糊 |
| 时间源 | 全局**累积 clock**，**永不复位**；扫掠相位 `= (clock/1000×50) % 360` | 复位会让雷达每 20 秒从 12 点"重新开机"，暴露实现；连续累积反而没有相位跳变 |
| 低端降级 | 帧时采样 → 2 级（跳帧 30fps → 关装饰）；**无玩家开关**，QA 用 `globalData.fxOverride` | 扫掠本身已有状态机管着，降级空间比预想小；开关是把技术问题推给玩家 |
| 皮肤模型 | `theme.color` 键名**全部不动**，值改为「按当前 skin 取」；`SEMANTIC` / `PLACEHOLDER` / `STATE` 都在皮肤之外，结构上写不进去 | 场景代码 100+ 处零改动；"皮肤吞语义色/占位色"在代码结构层面不成立 |
| 云同步 | **这一期零云函数改动** | 敌方棋盘从不传飞机位置，只传"我打过哪几格" |
| 现有测试 | **需要改的断言：0 项**（项数以 §7.1 实测为准，本表不抄数 —— 抄进来的数一定会过期） | 唯一读色值的断言读 `theme.color.planePalette`，P0 改色后仍然通过 |
| `svg-ctx` 补能力 | **本期补 0 个方法** | art 规格里唯一需要 clip 和 rotate 的两处，都被上面的几何方案消掉了 |

## 1. 事实校正：两套实测数据与它们的口径差异

### 1.1 我的实测（真实场景 + 真实数据，375×667，dpr2，`app.renderOnce()` 单帧）

| 场景 | 总调用 | fill | stroke | fillRect | fillText | **光栅化批** |
|---|---|---|---|---|---|---|
| lobby | 1073 | 78 | 20 | 1 | 17 | **116** |
| rooms（空） | 84 | 2 | 5 | 1 | 6 | **14** |
| deploy（3 架） | 876 | 70 | 33 | 1 | 30 | **134** |
| battle 刚开局 | 752 | 39 | 48 | 1 | 34 | **122** |
| battle 打了几炮 | 894 | 53 | 71 | 1 | 34 | **159** |

「光栅化批」= `fill + stroke + fillRect + strokeRect + fillText`，即真正触发像素填充的次数（`moveTo/lineTo` 只累积路径，不算）。

单块棋盘拆开：

| 对象 | size | 格子 | fill | stroke | fillText | 批 |
|---|---|---|---|---|---|---|
| 空盘 | 334 | 37.1px | 3 | 22 | 18 | **43** |
| 空盘（缩略） | 97 | 10.8px | 2 | 22 | 0 | **24** |
| 3 架飞机盘 | 334 | 37.1px | 37 | 29 | 21 | **87** |

### 1.2 art 的实测（`design/art/skin-system.md` §6.1，口径 = `beginPath/fill/stroke/fillText`）

对战页两块盘 ≈ **142**；新版飞机 +6；扫掠 +12 → **≈160**。

### 1.3 两个数不矛盾，是两把尺子

我的 159 把 `fillRect` 也算作一次光栅化批（因为 `draw.fillRect` 带圆角时实际走 `fill()`）；art 的 142 只数 `beginPath/fill/stroke/fillText`。**误差 12% 来自口径，不来自实现**。

**本文统一采用 art 的口径（142 → 160）**，因为它正是"Canvas 调用次数"这个能直接对应真机耗时的量。我那张表的价值在**拆分**（谁占多少），不在总数。

### 1.4 拆分给出的三个断言

1. **40 次独立 `stroke` 画 20 条网格线**（`board.js:235-239`，`for i in 0..9` 每轮两次 `draw.line`，每次 `beginPath + stroke`）。art §6.1 的 142 里，格线占 40 —— **28%**。
2. 同样一批线，`draw.radarGrid()`（`draw.js:173-187`）已经证明可以压成 **1 次 stroke**。`board.js` 没这么写，是**白送的 38 次/帧**：改 12 行、零内存、零风险、零视觉变化。
3. 缩略盘 24 批里 22 批也是这 20 条线 —— 合批后缩略盘从 24 降到 ~5。

**这是本期第一个该做、且做完立刻见效的动作。** 它不是"优化"，是两处同类代码的不一致。

## 2. 图层栈与重绘策略

### 2.1 采用 art §4.5 的图层栈（不另起一套）

| 层 | 内容 | 变化频率 |
|---|---|---|
| L0 | 页面背景：三段渐变 + 背景雷达网格 | 尺寸/皮肤变 |
| L1 | 底板外阴影 → 底板 → 外框描边 → 内框描边 | 尺寸/皮肤/敌我变 |
| **L2** | **雷达扫掠：10 段扇形 + 前沿线 + 束头**（裁到格区） | **每帧** |
| L3 | 网格线 20 条 + 棋盘外沿加粗框 | 尺寸/皮肤变 |
| L4 | 空格中心微点（81 个一次 fill） | 局面变 |
| L5 | 双轴刻度 1-9 | 尺寸/皮肤变 |
| L6 | 飞机 10 格 + 装饰 + 机头序号 | 局面变 |
| L7 | 命中 / 未命中 / 击毁标记 | 局面变 |
| L8 | 叠加层（select / ghostOk / ghostBad / fade / hint） | 仅拖拽中 |
| L9 | 页面 UI（标题、状态条、倒计时、按钮） | 文字 1Hz |
| L10 | 全局浮层（toast / busy） | 事件驱动 |

**我只改一处细节并给出理由**：art §6.3 的 P3 写"底板 + 格线 + 刻度 + 微点合并成一次离屏"，但这条**和 §4.5 的 L2 位置自相矛盾** —— 底板在 L1、格线在 L3，中间夹着 L2 扫掠。把它们合成一张位图，扫掠就无处可插。

**可缓存的单元只有 L3–L8**（格线 + 微点 + 刻度 + 飞机 + 痕迹 + 叠加层），L1 底板必须留在外面。已就此事回问 art。

### 2.2 为什么不做脏矩形（结论不变，理由更强了）

v1 的理由是"扫掠扇覆盖整盘"。采用 art 的图层栈后**更彻底**：扫掠在 L2，**在它之上还压着 L3–L8 六层**。任何一次局部重画，只要动到 L2 的影子，都得把上面六层在那块区域重画一遍 —— 脏矩形退化成"整盘重画 + 额外的 clip 开销"。

三条硬伤：
1. 扇区在转，脏区每帧都换位置，`clearRect` 的矩形要跟着算；
2. `clearRect` 之后被清掉的**背景（L0 渐变 + 网格）必须局部补画**，而 L0 的渐变按整屏坐标算 —— 局部重算渐变区间比整屏重画还贵；
3. 收益上限只有 L0 那 2 次调用。

**不做。**

### 2.3 全量重绘够不够：够，而且余量合理

art §6.1 的结论我复核后同意：**160 次 × 中端安卓 Canvas2D ≈ 3~5ms**，预算 16.7ms，余量约 3 倍。

补一条 art 没算的保守情形 —— 低端千元机按 50µs/次：

| 情形 | 次数 | 帧耗时 | 占预算 | 判断 |
|---|---|---|---|---|
| art 的估算（未合批） | 160 | 8.0ms | 48% | 守住，但只剩一半 |
| **PR-1 合批之后** | **122** | **6.1ms** | **37%** | 有像样的余量 |
| 再上 P5 缓存 | ~12 | 0.6ms + 1 次位图采样 | — | 收益递减，且引入内存与正确性风险 |

**所以顺序必须反过来**：先把那 38 次白送的 `stroke` 拿掉，再谈缓存。合批做完之后，缓存省下的 110 次只把 6.1ms 压到约 1ms —— 而 6.1ms 本来就在预算内。**这就是 P5 降级为"备用方案"的完整理由。**

- **P5（离屏缓存）不是必须做，但要留好位置**。设计在 §2.4–§2.7 写全了，真机 p95 超标时按图施工，不用重新设计。
- 判断门槛用 art §6.5 的方法：**p95 帧耗时 ≤ 8ms 且 p95 调用数 ≤ 300** 就算稳。

### 2.4 缓存单元（P5 才启用）：L3–L8 合成一张透明位图

```
┌ L1 底板 ──────────── 直画（4 次调用，不值得缓存）
├ L2 扫掠 ──────────── 直画（每帧，12 次）
└ L3–L8 ────────────── 一张透明位图，1 次 drawImage
```

**底板为什么反而不缓存**：它只有 4 次调用（阴影 fill + 底板 fill + 外框 stroke + 内框 stroke）。缓存它要 4.6MB，收益 3 次 —— 全表最差的一笔交易。**便宜的层不缓存，贵的那层才缓存**，这条规则让 art 的图层栈和缓存方案不再打架。

位图是**透明背景**（不填底板），`drawImage` 直接合成在扫掠之上。

**内存账（P5 启用时）**

参考基准 390×390 逻辑像素：

```
390 × 390 @ dpr3 = 1170 × 1170 px = 1,368,900 px × 4 B/px = 5.48 MB
```

| 对象 | 逻辑尺寸 | dpr | 位图 | 占用 |
|---|---|---|---|---|
| **基准块 390×390** | 390×390 | 3 | 1170×1170 | **5.48 MB** |
| 对战大盘（390 宽机型，格区 + PAD 环带） | 357×357 | 3 | 1071×1071 | 4.59 MB |
| 对战缩略盘 | 141×141 | 3 | 423×423 | 0.72 MB |
| 全屏背景（**永不缓存**） | 375×667 | 3 | 1125×2001 | **9.00 MB** |
| iPad 大盘（768 宽，dpr2） | 431×431 | 2 | 862×862 | 2.97 MB |

- **3 块 390×390 = 16.4MB → 不批**。上限 **2 块、≤ 6MB**。
- 实际峰值：只在**放大的那一块盘**上缓存（art §4.7 已经规定同一时刻只有一块盘是焦点盘）→ **4.6MB**，缩略盘不缓存。
- canvas 后备存储在不同平台可能双缓冲（×2）→ 上述数字按 ×1 记，风险余量按 ×2 留，并在 `wx.onMemoryWarning` 里无条件 `releaseAll()`。

### 2.5 缓存失效：内容签名 + 滞后一帧（P5 时启用）

人工"在改棋盘的地方标脏"是这套方案唯一的高危点 —— 漏一处就是画面卡在旧状态，且自动化测试几乎测不出来。

**改用内容签名**（覆盖 art §6.2 列的全部缓存键，外加敌我变体）：

```
sig = size | variant(mine/foe) | skinId | cellsFlat | marksKeys | dimKeys | selected | planesSig
```

`board.js` 新增 `contentSig(o)`，每帧算一次（81×2 次字符拼接 ≈ 0.02ms，比 87 次绘制便宜两个数量级）。加**滞后一帧**判定：

```js
if (sig !== lastSig) { 直画到主画布; lastSig = sig; return }   // 局面在变，缓存无从谈起
if (sig !== cache.sig)  { 重建缓存 }
drawImage(cache)
```

一个 if 解决三件事：
1. **拖拽布阵**：每帧 sig 都变 → 一直走直画，成本 = 现状 + 一次 sig 计算。**零回归**。
2. **松手 / 开火后**：第一帧 sig 与上帧相同 → 重建 → 之后进 `drawImage`。
3. **漏标脏不可能发生**：sig 从真实输入算出来，不是人打的标记。

**安全阀**：`app.globalData.noCache = true` → `acquire()` 恒返回 `null` → 全部直画。QA 与等价性测试用它对比。

### 2.6 dpr 处理（不能缓存成 1x 再拉伸）

```js
cv.width  = Math.ceil(outerW * dpr)          // 设备像素，必须 ceil
cv.height = Math.ceil(outerH * dpr)
oc.setTransform(dpr, 0, 0, dpr, -ox * dpr, -oy * dpr)   // 赋值之后才能设，赋值会重置 transform
board.render(oc, o, u)                        // 绝对坐标原样复用，一行不改
ctx.drawImage(cv, ox, oy, outerW, outerH)     // 主 ctx 已在 dpr 空间，目标用逻辑像素
```

**绝不可以 1x 再拉伸**：棋盘最细的元素是 1px 网格线和 9~13px 刻度数字，1x 位图在 dpr3 上放大 3 倍会被重采样成 3px 灰带和墨点 —— 恰好是玩家用来报点的东西。

### 2.7 API 探测与降级（P5 时启用）

```
① wx.createOffscreenCanvas({ type:'2d', width, height })
② wx.createCanvas()      ← 小游戏里第 1 次是上屏 canvas，之后是离屏
③ null                   ← 拿不到就整条链路降级
```

⚠️ **测试陷阱**：`scripts/lib/wx-stub.js:79` 的 `createCanvas()` 返回的 canvas 包着**同一个记录型 ctx**。缓存一旦走 ②，离屏绘制会被记进 `CTX.calls`，污染 `test-minigame.js:118-127` 的计数断言。两处都要改：stub 的 `createCanvas` 加调用计数（第 2 次起返回全新 ctx）；`createApp({ offscreen: fn })` 允许注入 `null` 强制降级。

### 2.8 扫描扇的边界裁剪：用几何求交，不用 `ctx.clip`

> 这是本方案在几何上最干净的一处，也是 team-lead 那条约束（不要依赖 clip）的落地方案。

**art §4.6 用 `ctx.clip()` 裁到格区。原因我完全同意**：刻度画在 `PAD` 外扩环带里（9~13px），不裁的话扫掠会越过边界去洗那些数字，而刻度是"横3竖4"报点口径的唯一载体。**裁切是保护措施，不是装饰。**

**但不需要 clip —— 因为格区正方形恰好以扫掠圆心为中心。**

`board.js` 里 `m.x = o.x`、格区是 `rect(m.x, m.y, m.size, m.size)`，而扫掠圆心按 art §4.2 是 `(m.x + m.size/2, m.y + m.size/2)` —— **正是这个正方形的几何中心**。于是射线到边界的距离有闭式解：

```js
const h = m.size / 2                                    // 半边长
const boundaryAt = (deg) => {                           // 沿 deg 方向到格区边界的距离
  const t = deg * Math.PI / 180
  return h / Math.max(Math.abs(Math.cos(t)), Math.abs(Math.sin(t)))
}
```

**已经验证过三个数值事实**（脚本核验，S=325）：

| 事实 | 数值 | 含义 |
|---|---|---|
| art 的外半径 `R = 0.72S` | 234.0px | — |
| 格区角点距中心 | 229.81px | `R > 角点距`（art 说的"比角点多 4px"是对的） |
| 边界半径区间 | **162.5 ~ 229.81px**（`h ~ h√2`） | 对任意角度都有 `R > boundary` → **永远被边界截断** |

**推论**：`R` 实际是一个永不生效的上限（保留它只为可读性和未来改布局时的安全垫）。扇面外沿**每条边都精确落在格区四条边上**，几何上等价于一刀 `clip`，但代价是零。

**每段扇区怎么构造**（N=10 段 × 8°）：

```
顶点序列（顺时针）：
  A = 圆心 + r0·(cos θa, sin θa)      // 内弧起点
  B = 圆心 + r0·(cos θb, sin θb)      // 内弧终点
  C…= 外沿上的点，角度从 θb 走到 θa     // 由 boundaryAt() 求半径
```

外沿用**直线段**近似弧：8° 在 R=234 上的弦高 = `R(1-cos4°)` = **0.57px** —— 视觉上完全等价于弧，且少了一半顶点。

**每段最多多插一个顶点**：格区四角固定在 45°+90°k（因为正方形以圆心对称），而每段只有 8° 宽 → 一段内**最多含一个角点**。判定只需比较 `θa < 角点角 < θb`（4 个候选角，一次取模即可）。若含角点，在 C 序列里插入该顶点，让扇面"拐"过直角。

**每段成本**：1 `beginPath` + 4~5 `moveTo/lineTo` + 1 `fill` = **1 次光栅化**。N=10 → 10 次。加上前沿线（1）+ 束头（2）= **13 次**，与 art §6.1 的 +12 一致。

**三处配套细节**：
1. **`r0` 内孔保留**（art §4.2 的 0.06S ≈ 0.55C）。理由照抄 her 的两条：避免 10 段在圆心汇聚成风车/摩尔纹；把中心格的空格微点让出来。
2. **不调用 `ctx.arc()`**。svg-ctx 有 arc，但用直线段替代后顶点更少、且不需要为"弧跨过 180°"操心。
3. **束头要往里挪**。art §4.9 的束头画在 `R` 处；现在外沿被截到格区边界，束头应画在 `min(R, boundaryAt) - 3px` 处，否则会贴在格线上。

**这段逻辑约 45 行**（含 `boundaryAt` / 顶点构造 / 角点插入），是本方案里唯一有几何复杂度的地方。但它同时买下三样东西：出图桩能复现、真机省一次 clip 状态切换、不引入任何新 ctx API。

## 3. 动画时间源

### 3.1 结论：全局累积 clock，**永不复位**

```js
// core/fx.js
let t = 0                                    // 毫秒，单调递增，App 生命周期内只增不减
function step(dt) { t += Math.max(0, Math.min(64, dt)) }   // 下钳 0 是本期要补的 bug
function time() { return t }
function freeze(ms) { t = ms; frozen = true }              // 仅供预览出图
```

扫掠相位：`θ = (fx.time() / 1000 * 50) % 360`（art §4.3 的 50°/s、7.2s 一圈）。

### 3.2 为什么不用 `Date.now()` 取相位

- 切后台 60s 回来，`now` 前进 60000ms，相位前进 `60000 % 7200 = 2400ms` 的相位 → **视觉上雷达瞬间跳小半圈**；
- 系统时间被网络校时/用户手动改动，相位任意跳；
- `Date.now()` 在部分旧安卓上粒度 10~16ms，50°/s 下每帧 0.83°，粒度会造成台阶感。

累积 clock 的 `dt` 已钳在 64ms 内，**天然免疫"切后台回来跳一大格"**：无论后台多久，最多推进 64ms（50°/s 下 = 3.2°，看不出）。

### 3.3 与 art §4.3 的一处偏差（**已裁决：采纳本文**）

art 写的是「用**从进入该状态起**累计的时间，不用 `Date.now()` 取模（否则两次进入同一状态时相位跳动）」。

**她的担忧成立，但解法不对。** 场景是这样的：art §4.7 规定扫掠只在「对方回合」开、轮到我方就关 —— 一局里这个状态**每 20 秒切换一次**。若每次进入都从 `t=0` 起算，玩家会看到雷达**每次开火后都从 12 点方向重新开机**，一局重复十几次。这个规律比相位本身更显眼，是"暴露实现"而不是"隐藏实现"。

| 方案 | 相位跳变 | 可预测性 | 评价 |
|---|---|---|---|
| `Date.now() % 周期` | **会跳**（切后台、校时） | 无 | ✘ |
| 每次进入状态 `t=0` | 不跳，但每次都从 0° 起 | **强到刺眼** | ✘ |
| **全局累积 clock** | **不跳** | 无（模拟真实雷达） | ✔ |

**为什么全局 clock 不会产生"相位跳变"**：`t` 单调且连续，扫掠关闭期间它照常推进 —— 但此时没人画它，所以"跳变"不存在。重新打开时靠 art §4.7 的 **240ms `masterAlpha` 线性淡入**遮住入场，相位从任意角度接上，与真实雷达完全一致。

**已裁决：采纳本文。** art 在规格 §4.3 里按此改写，并在变更记录里留了一句「他是对的，我原处方自相矛盾」（原文见 §8.2-1）。若将来有人要改回复位，改动只有一行（进入状态时记 `sweepT0 = fx.time()`，相位用 `fx.time() - sweepT0`）—— 但改之前先读 §8.2-1，那里解释了为什么复位是错的。

### 3.4 暂停 / 切后台 / 场景切换

| 事件 | 做法 | 效果 |
|---|---|---|
| 切后台 | `wx.onHide → app.stop()`（**新增**，现在全仓没有） | rAF 停投；`t` 冻结 |
| 回前台 | `wx.onShow → app.start()`（与现有分享处理并列） | `start()` 里 `last = Date.now()` 重置 → 首帧 `dt≈0` → **不重启，只停了一下** |
| 场景切换 | **不复位** `t` | 各处扫掠相位天然同步 |
| 首次启动 | `t = 0` | — |
| 预览出图 | `fx.freeze(固定值)` | 见 §7.4 |

> **后台是否白烧电**：小游戏切后台时系统会冻结渲染帧投递，rAF 基本不再回调，**不存在持续烧电**。显式加 `onHide/stop` 是为了另外两件事：① 回前台必须做一次「对局重同步 + 缓存作废」，否则会看到切走前的旧画面（`battle.sync()` 只在 `onEnter` 调一次）；② 省掉切出瞬间可能补投的 1~2 帧带来的 `Date.now` 跳变尴尬。
> ⚠️ 「切后台 rAF 是否**立即**停投」我没在真机验证过（各基础库版本行为有差异）。上面两条理由不依赖这个假设，所以显式加 `onHide/onShow` 无论哪种行为都正确。

### 3.5 不要用帧计数器当时间源

帧率掉到 30fps 时动效会跟着慢一半，"降级到 30fps"就变成了"动效变慢"—— 那是 bug 不是降级。

### 4.4 降级阶梯（只有两个杠杆）

art §4.7 的状态机本身已经管住了大部分开销（大厅/房间/布阵/结算全关，我方回合也关）。所以降级空间比 v1 估的小：

| 级别 | 杠杆 | 视觉损失 | 省什么 |
|---|---|---|---|
| **L0** | 全量 | — | 基准 |
| **L1** | 绘制降到 30fps（`now - lastPaint >= 33`）；**动效相位仍按真实时间算，只是刷新变粗** | **零**（50°/s 下每帧 1° vs 1.7°，肉眼分辨不出） | 每秒总成本 ÷2 |
| **L2** | 30fps + 关装饰：扫掠换静态雷达底纹、去飞机装饰层、命中扩散改静态爆点 | 氛围全失，信息零损失 | −25 次/帧 |

**绝对不降的**（进控制清单）：双轴刻度、81 个空格微点、机头序号、命中/空炸/击毁三态配色。

### 4.5 判断依据：运行时帧时采样，不看机型

- **不用机型白名单**：机型库上千条、新机每月出，且同一机型在「低电量模式 / 高温降频 / 后台 20 个 app」下能差 3 倍。用机型判性能 = 用出厂参数猜此刻状态。
- **不用系统版本**：跟性能弱相关，跟 API 能力才相关。API 能力用特性探测（`draw.js:157` 已有套路）。
- **用帧时采样**，采样点在 `tick()` 里、`dt` 钳制之前：

```js
const raw = now - last
const dt  = Math.max(0, Math.min(64, raw))   // 上界原有，下界本期补
last = now
fx.step(dt)                                   // 每个 rAF 都推进
scene.update(dt)                              // ← 逻辑必须每个 rAF 都跑
if (shouldPaint(now)) {                       // ← 只有绘制可以跳（L1 起）
  perf.sample(now - lastPaint)                //   只统计"真画了"的那次
  lastPaint = now
  paint(now)                                  //   background + scene.render + overlays
}
```

**`scene.update` 不能跟着跳帧**：`battle.update()` 的 250ms 累加器、倒计时、`requestTick()` 节流全靠 `dt` 喂。把逻辑频率和绘制频率绑在一起是更糟的耦合 —— 现在就把 `frame()` 拆成 `update` / `paint`。

**判级用"相对目标间隔的倍数"**，三个级别共用一张表：

| 条件 | 动作 |
|---|---|
| 连续 3 次采样 `> 2.5 × 目标间隔` | 立刻降一级 |
| 60 次采样均值 `> 1.3 × 目标间隔`，连续 2 窗口 | 降一级 |
| 60 次采样均值 `< 0.9 × 目标间隔`，连续 3 窗口 | 升一级 |
| 已到 L2 | **锁死**，不再回升（防抖动） |

目标间隔：L0 = 16.7ms、L1/L2 = 33.3ms。**必须按"实际画了的帧"采样** —— 否则进入 L1 后 rAF 间隔回到 16.7ms，永远报不出问题，阶梯卡死。用这个办法也不需要高精度计时器（`Date.now()` 在某些安卓上粒度就有 16ms，量不出 6ms 的 `frame()` 耗时）。

跳过前 90 帧（首帧建缓存、字体加载、解码都在这一段），每次 `onShow` 重开一个采样窗口（设备可能已经烫到降频）。

### 4.6 不给玩家开关

同意主理人。三条理由：
1. 开关把"该不该关动效"这个技术问题推给玩家，而玩家唯一的依据是"卡不卡"—— 那正是自动检测在读的信号，且它读得更早。
2. 多一个设置项 = 多一个状态位 + 一处持久化 + 一条测试路径。按现在的结构要改 4 处（设置页 / 存储 / 读取 / 各 widget 分支）。
3. `ai-tune` 调参页已经存在（`scenes/ai-tune.js`），QA 要"强制看某一级"塞那儿，**零 UI 成本**。

**`globalData.fxOverride = 0|1|2` 优先级最高**（读了就锁死）。`ai-tune` 页加一行三段控件（~20 行）。

> art §4.11 提的「减少动态效果」系统开关是**另一件事**，那个要给（无障碍需求，且信息零损失）。它接的是扫掠的 `masterAlpha`，不是性能分级。

### 5.4 飞机朝向：几何旋转，不用 `ctx.rotate`

art §5.5 写的是「整架飞机画在旋转过的局部坐标系里（`ctx.translate` + `ctx.rotate`），只有序号反旋转」。**这个做法我否掉了**，换成等价的几何旋转。三条理由：

1. **`svg-ctx.js` 的 `scale`/`setTransform` 是空实现（`:77-79`），没有 `rotate`/`translate`** —— 用了就等于放弃出图预览。而"改完美术效果没人能看一眼"正是这个项目最初的痛点（`svg-ctx.js` 开头的注释就是为它写的）。
2. **team-lead 明确要求保持 `plane-icon.js:20 shapeOf()` 的"格子集合旋转"路子**，不引入 canvas 变换。
3. 旋转只有 90° 的整数倍 → **正交映射，无插值，1px 线不糊**（art 自己也强调这点，几何旋转同样成立而且更显然）。

**做法**：所有装饰层在**局部坐标**（5C × 4C 的包围盒，原点左上）里定义成点集，投到屏幕时过一次 `rot90(pt, rot)`：

```js
// rot: 0/1/2/3 → 90° 整数倍映射，纯整数运算
rot0: (lx,ly) → (lx,     ly)
rot1: (lx,ly) → (H - ly, lx)      // H = 4（局部格高）
rot2: (lx,ly) → (W - lx, H - ly)  // W = 5
rot3: (lx,ly) → (ly,     W - lx)
```

- **龙骨渐变**：亮端永远在机头侧 → 用旋转后的两个端点建 `createLinearGradient`，方向自动正确。`draw.vGradient` 只做纵向，这里要一个带任意端点的变体（`draw.gradientBeam(ctx, p0, p1, stops)`，约 20 行，沿用 `typeof ctx.createLinearGradient !== 'function'` 的降级写法）。
- **机头序号**：屏幕坐标系单独画，恒正立（art §5.5 表格最后一行，正确）。
- **代价**：比 art 的 `rotate()` 写法多约 **45 行**（6 个装饰层的点集定义 + 4 个映射函数）。换来出图真实 + 不碰被禁的 API。

### 5.5 存储与依赖方向

**art §2.5 建议存 `shared/services/profile.js`，位置对，但要加一道约束。**

```
key:   'zfj_skin'
value: { v: 1, id: 'abyss' }
```

- **读取时机：启动读一次**（`game.js`，和 `playerId` 同一处 `:40-44` 旁边）→ `app.globalData.skin`。`wx.getStorageSync` 是**同步阻塞**的，进场景再读会在切换处制造抖动；而皮肤一局最多变一次，没有失效问题。
- **`v` 是结构版本号**：读到 `v !== 1` 就丢弃走默认。比写迁移函数便宜，皮肤是纯外观，丢了不心疼。
- **任何异常都落到 `abyss`**（缺省 / 读取失败 / `v` 不符）。**任何情况下界面都必须能画出来。**
- 切换 = 写一次 storage + 作废所有离屏缓存。

**依赖方向的约束**（防污染）：`profile.js` 里只存**一个字符串**，暴露 `skinId() / setSkinId()`；**白名单校验留在 `core/skin.js`**。这样 `js/shared/**` 知道"有个叫皮肤的设置项"，但**不知道皮肤列表、不 require 任何渲染代码**。

`js/shared/` 是玩法数据层，也是 `scripts/sync-shared.js` 与 `miniprogram/` 共享的部分 —— 一旦 `shared/` 依赖了 `core/` 或 `widgets/`，小程序端就得跟着引一份渲染代码，首包和依赖方向双崩。**这条要落成可执行断言**（§7.2）。

### 7.4 动效的预览可复现

现在 `app.renderOnce()`（`app.js:179-181`）是 `this.frame(16, Date.now())` —— 每次跑出图，动效相位都不一样，没法 diff、没法回归。

```js
renderOnce(fxMs) {
  if (fxMs != null) fx.freeze(fxMs)              // 冻结动效时钟
  this.frame(16, Date.now())                      // now 仍给 toast/busy 用
}
```

- `drawOverlays(now)` 继续吃 `Date.now()` —— toast 的过期判定不能被冻结（否则预览图里永远挂着一个提示）。

### 7.5 修掉一条偶发红：AI 强度断言的样本量

`test-core` 有一条「1 架局平均用炮 ≤ 13（改造前约 15）」，**偶发红约 10~17%**
（连跑 12 次红 2 次、25 次红 1 次）。实测均值约 11、阈值 13、余量 2 炮 ——
**问题从来不是阈值高，是样本量 1。**

「60 局」听起来不少，但抖的不是「60 次里的哪几次」，是**「这一次的世界」**（阵型随机 + AI 平手时的随机选格）。
一个世界跑 60 次，测的是这个世界，不是 AI。

单纯固定一个种子不算修：那只是把 17% 的随机失败换成一次固定答案，覆盖率归零，
而且下次改 AI 强度时这条断言会因为「恰好那个世界」假绿或假红。现在：

| | 做法 |
|---|---|
| 种子 | 5 个固定种子（`20261113 + 0..4`），每个一组 |
| 每组局数 | **30**（不是 60）：实测 5×60 整份 `test-core` 要 **3.29s**、5×30 是 **1.87s**，都超过「这段超过 2 秒就降到 30」的线（差 1.42s 全是多跑的那 150 局）。5×30 的中位数比 1×60 可信 —— 抖动来自「这一次的世界」，不是「60 次里的哪几次」 |
| 主断言 | **中位数** ≤ 13（3 架局 ≤ 34） |
| 补充断言 | **任一组**上限：1 架局 ≤ 15、3 架局 ≤ 39 —— 中位数管趋势、上限管离群 |
| 输出 | 5 个值全部打印 |

**为什么要两条一起**：只有中位数的话，「5 组里 3 组烂、另 2 组很好」照样能绿；
只有上限的话，一次离群就红回去，等于没解决偶发。两条一起才同时管住趋势与离群。

实跑（确定性，连跑 6 次逐位相同）：

```
1 架局 5 组：[11.17, 12.47, 11.17, 11.13, 11.20] 中位 11.17 上限 12.47
3 架局 5 组：[27.83, 28.30, 29.10, 28.53, 29.47] 中位 28.53 上限 29.47
```

反向验证：阈值收到 11.0 → 红「1 架局中位数 ≤ 13」；离群上限收到 12.4（实测上限 12.47）→
红「1 架局任一组 ≤ 15」。两条都是真的在比。

顺手把 5×60 也真跑了一遍（只为量耗时与对照，不进代码）：
`[10.95, 13.15, 12.05, 12.05, 11.08]` 中位 **12.05** / `[28.15, 28.53, 27.32, 28.33, 31.82]`
中位 **28.33** —— 与 5×30 的 11.17 / 28.53 同量级。**局数翻倍没有让结论变，只让耗时翻倍**，
所以 30 是对的；把 60 写进代码只会让人以为「跑得久所以更准」。

### 8.3 这张表的性质：销账，不是待确认

**硬规则**

> 本节只写「已裁决 + 出处」。真未裁决的事项允许出现在这里，但必须写清**等谁**，以及**他不在时谁接班**。

**「待 X 确认」而 X 已离场，等于永久待确认 —— 而它看起来像在等一个会来的人。**

这是「无主清单会烂」的第二个实例。第一个是 `planeOffHead`：它躺在「暂保留」里三个版本，最后是靠漏洞蒙过去的 —— 它和 `abyss.frame` **同值**，所以「按值登记」的检查放行了它；等 `dusk` 落地，它就会带着 `abyss` 的配色绿着出去。两张表是同一个病：**清单的状态如果是「等一个人」，而那个人不会来，它就变成存档错误，还每天看起来更正常一点。**

所以本轮把 6 项一次核到原文、写死出处。**核对本来就是可以机械完成的事** —— 六条 grep 就能定位到章节，剩下的只是判断「这句引用是否真的回答了那个问题」。上一版把这一步写成「留给下一轮的第一个动作」，是把一件十分钟的事变成了交接事项。

**§8 与 §11.1 的分界**：§8 记的是「**已经有答案，只是没销账**」；§11.1 记的是「**还没有答案，但知道在等谁**」。混着写，就会有人认为 §8 也在等人。

### PR-2b = 「十块缝成一块」+ 明度阶梯 · **已实现**（~95 行代码 / ~90 行测试）

art 的验收结论是「技术实现是对的，但华丽没成立 —— 不是装饰不够，是十块没缝成一块」。
她给了三条 P0（描边打在每一格上 / 龙骨被切三段 / 后掠线按格断），**三条的归因都不对**，
逐条核过代码：

| art 的诊断 | 代码实际 |
|---|---|
| 描边打在每格、内部多出 12 条边 | 不成立。`planeEdge()` 只画「邻居不在集合内」的边，一直是并集轮廓 |

**唯一根因：底色层逐格内缩。** 旧代码对每一格调
`roundRectPath(x+ins, y+ins, w-2ins, h-2ins, rad)` —— 四条边**都**缩。

龙骨尾端 α 只有 0.021，极淡区段直接透出暗缝 → 读成「断成 3 段」；

### PR-4 前置 = 皮肤 token 契约检查 · **已实现**（`scripts/check-skin-tokens.js`，~870 行）

人眼比对相距几百行的两块文本查不出分叉，**必须机械验**。

**为什么不能用一行 grep。** 计数 `grep -o | sort | uniq -c` 只能证明「每个值各出现两次」，
证不了「1 号机身没配给 2 号机头」—— 配对漂移时每个值仍然各两次，检查全绿而颜色已错。

**怎么跑 / 退出码是什么意思**（接手的人先看这段）

```

node scripts/check-skin-tokens.js --strict   # CI / 提交前
```

| `0` | 全绿（`--strict` 下也绿） | —— |

#### 别名：派生关系要**能验**，不能只靠值相等

`hintRing` / `selectRing` 不是独立颜色，就是主色。上一版各抄一份字面量 —— 那是迟早漂的写法：
换 dusk 时 `primary` 变了它们不变，环就不再是主色，而按值检查会因为
「这个值在 `primary` 上登记过」放过它们。

但光写成 `ABYSS.hintRing = ABYSS.primary` 也不够：**值仍然同值**，
脚本看到的是「两个键恰好一样」，分不出「派生」和「撞值」—— 第一版断言四就是这么把
两个已经派生好的键判成了失败。

所以把**指向关系本身**声明成数据：

```js
const ALIASES = { hintRing: 'primary', selectRing: 'primary' }
```

脚本验两件事，缺一即红：
1. 别名指向的 token **自己**有契约位置（别名不能指向一个同样没登记的键）；
2. 别名的值**真的等于**源 token（否则说明有人把值抄回去改了，声明已成谎话）。

**这不是白名单。** 加白名单是让检查闭嘴；声明关系是让检查能查得更准 ——
白名单不需要被验证，别名需要被验证两条。别名对所有皮肤生效（`Object.keys(SKINS).forEach`），
所以加 `dusk` 时不需要记得改第二处。

#### 12 个待登记 → 0：三条路各走了一条

上一版这里有 12 个「契约覆盖缺口」。裁决完之后它们各归各位，**没有一条是加白名单**：

| 键 | 归宿 |
|---|---|
| 束头几何 `sweepTickInset` `sweepTickLen` `sweepTickWidth` | **挪层 + 改名**：`SWEEP.tickInset / tickLen / tickWidth`（三个都标「暂定」） |
| 拖拽/非法/蒙层/非焦点机 8 个：`conflict` `conflictLine` `ghostOk` `ghostBad` `ghostBadLine` `dragOrigin` `mask` `planeDim` | **立新层 `STATE`**（顶层，不可换肤），理由：这些不是皮肤的一部分，是**画在皮肤之上的状态** |
| `disabled` | **删除**（0 处绘制引用，A3 早判过） |

`STATE` 为什么不能进 `SKINS`：蒙层、去焦点、非法提示如果随皮肤走，会出现
「换个皮肤之后『这格不能点』变得看不出来」——**状态表达权不在皮肤手上**。
和 `PLACEHOLDER` 同构但不同：`PLACEHOLDER` 是「缺失」，`STATE` 是「叠加」。

**`conflict` 与 `ghostBad` 字节相同**（`rgba(255,90,90,0.30)`）却都保留、都登记 ——
规格里注了「同值，语义不同：一个是『已违规』，一个是『将要违规』」。
**这不是撞值，是两个状态恰好同色。** 它们能过检查，正因为各自有名字 ——
而如果只按值查，删掉其中任何一个都不会被发现。

还有一条从「待登记」这个分类本身长出来的教训（规格 §9.1 反面表原话）：
**「待登记」假定「现有的键都该被登记」，而死键的正确归宿是删除。**
判据不是「它在不在 `theme.js` 里」，是「**它画不画到屏上**」。

| `SWEEP.trail` | `8` → **`7`**，与 `ahead` 同长 |
| `SWEEP.ahead` | 删掉末尾 `0.001`，**7 位** |
| **新增 `SWEEP.seg: 5`** | 每层角宽。**总跨度不该是第三个常数** —— 80° 会漂，正因为它是个独立数字而不是算式。现在契约里只有 `arc / trail / seg`，跨度 = `arc + trail × seg` = **75°** |
| `board.js` | **删掉 `slice(0, 7)`**，`SWEEP_TRAIL` 中间常量也删，循环直接吃 `sweep.ahead` / `sweep.seg` |

**为什么 `slice(0,7)` 必须删**：它不是解法，是把「契约 8、代码 7」这个差异**藏起来的胶带**。
契约改成 7 之后它是空操作 —— 留着只会在下次有人调 `trail` 时静默截断，
而且没人会怀疑一行 `slice`。

顺带一条 art 自己的更正：她先把 `4.7/255` 挂在「7 层」名下，然后发现那个数没重算 ——
又是「暂定伪装成推导」。最后只留能算的：**阶梯头两格 `0.090 − 0.072 = 0.018`（≈4.6/255）**，
它出现在最亮的两层之间、**与总层数无关**；第 8 层只贡献 `0.007 − 0.001 = 0.006`（1.5/255）
的台阶，而它自己的 α 是 0.26/255，低于 8bit 量子 —— 所以删掉它屏幕上零变化。

#### 已知盲区：rgba 没参与**逐值**比对（每次运行都打一行数）

`collectHexValues` 只认 `#rrggbb`。`theme.js` 里还有 **20 个 rgba 字面量**，
它们**没有参与断言一的逐值比对**，所以「每个色值都登记过」严格讲只对 hex 成立。

**但这一版的盲区比上一版小了一大截，而且是被结构改小的，不是被放宽改小的：**

| | 上一版 | 现在 | 为什么变小 |
|---|---|---|---|
| 代码里未登记的 rgba | **12 / 22** | **2 / 20** | `STATE` 的 8 个以字面量进了契约（由断言一·反向逐值比）；`sweepEdge` / `sweepHead` 不再存在 —— 它们变成 `sweepColor` + `SWEEP.edge/head` 两个 alpha，在使用处由 `draw.alpha()` 拼出来 |
| 剩下的 2 个 | `keelTail` / `lightDim` | 同左 | 「α×0.07」「α 减半」的派生值，规格 §9.3 **G1** 已登记，PR-5 收成公式 |

剩下这 2 个仍不硬纳（逐值比会误报：规格写的是公式不是值），但每次运行都打印数量 ——
**盲区不写出来，下一轮就会被当成「已经验过了」，然后有人基于它做决定。**

**三个设计决定，都有代价，写清楚：**

1. **「已登记」只认 token 表，不认散文。** 规格正文里还留着被否决/历史的色值
   （「原来是 X」这种），把它们算成登记过，就等于允许代码继续用被否决的那一版。
   副作用：`theme.js` 注释里的两个历史值（`#35506B` / `#2FD08F`）会被列出，但**只作提示不算失败** ——
   它们是文档，不是会被画到屏上的东西。
2. **例外按路径声明，不按色值声明。** 写色值就等于把色值抄进检查里（会数到自己）。
   上一版这里有一张 3 条的 `DECLARED` 白名单，**现在整段删掉了**：那 3 个键已由 art 立
   `PLACEHOLDER` 层正式登记，别名键由 `theme.aliases` 声明 —— 两条路都不需要白名单。
   **`--strict` 现在是绿的**（19 项，0 待处理项）。
3. **「已落地」在规格里没有标记**，所以反方向的检查按 §9 唯一的 `skin: 'abyss'`
   + 「语义色 / 占位色 / 状态色是顶层、不属于任何皮肤」来界定：
   abyss 的 hex token + 语义色 11 + 占位色 4 + 状态色 8 + 扫掠 11 + 装饰 6 + 别名 2。
4. **检查的范围必须跟着数据搬家。** 断言四这一版从「只查 `theme.color`」扩到
   「`color` + `sweep`」：v2.4 刚好把 11 个扫掠参数挪进顶层 `sweep`，
   如果检查不跟着挪，「把键挪出 `color`」就成了绕过断言四的正路。
   `planeArt` 故意不在里面（它的 2 个派生值属于 G1，塞进「待登记」会让这条永远清不了零），
   但也不放过：脚本从 §9.3 的 G1 原文里抓出它点过名的键当底，
   **多出来的键一律硬失败** —— 否则「往 `planeArt` 加新键」就是同一扇后门。

**四个自己踩的坑**

1. 第一版用 `hexSet(srcRaw.replace(srcCode, ''))` 求「注释里的色值」——
   剥完注释的文本不是原文的子串，`replace` 一次都没命中，于是报出来的「43 个」其实等于全部色值。
   **数是错的，但看起来很像真的**（43 是个合理的数）。注释要单独取，不能靠减法。
2. 第一版把 3 个未登记键做成「已声明例外」，并在断言四里把 `hintRing` / `selectRing`
   判成失败 —— 两个方向都错：白名单掩盖了真问题，而按值判读不出「派生」。
   修法不是放宽，是**换个能表达出来的东西**：让 art 立层（`PLACEHOLDER`）、
   让代码声明关系（`aliases`）。**检查表达不了的东西，先想办法让它能表达，再谈放不放宽。**
3. **断言一·反向原来只认 `key: '#hex'`**，于是 `STATE`（全 rgba）、`SWEEP`（数字 + 数组）、
   `PLANE_ART`（全 rgba）三块**整块漏在检查之外**。这不是「没空写」，是**结构性漏掉**：
   正则只认一种形态，另外三种形态就被静默跳过 —— 而**在检查里，「漏掉」等于「验过了」**。
   修法是把解析器扩成能认 `'#hex'` / `'rgba()'` / `'字符串'` / 数字 / 数组五种，
   并对每种做各自的归一化（数字 `0.10` 与 `0.1` 是同一个数，比字符串只会红在格式上）。
   这一版的 68 个 token 里，有 29 个是这次才第一次被验到的（8 + 13 + 6 + 2）。
4. **`parseEntries` 里那句 `if (name === 'body' || name === 'head') continue` 是从
   `contractTokens` 抄过来的，但它在 flat 块里是错的**：那句跳是为了避开
   `palette[i]` 里的 `{ body, head }`，而 **`SWEEP` 有一个正当的键就叫 `head`**。
   于是 `sweep.head: 0.30` 连续两轮**被静默跳过**，检查报「11 个 SWEEP token 对上」——
   少的那一个从来没被验过，而它一直绿着。team-lead 预测「11 → 12」，实际是 **12 → 13**，
   差的正是这一个。
   修法两层：① flat 块不再跳过任何名字；② 新增 `declaredNames()` 对账 ——
   数行首 `name:` 的个数，与解析出来的名字集合做差，**少一个就红**。
   一句话：**「跳过」是能被继承的坏习惯，而它长得人畜无害。**

## 10. 一页规则（程序员可直接执行）

1. **绘制分两类**：每帧变的（扫掠、命中扩散、选中呼吸）预算 **≤13 次**；状态变才变的（涂装、底纹、刻度）**必须能进缓存**。想在棋盘上做"每格呼吸"——先来问我。
2. **不用 `ctx.clip`**。要裁剪就把几何算准（扫掠用射线-矩形闭式解，见 §2.8）。
3. **不用 `ctx.rotate` / `translate` / `scale`**。旋转用点集 90° 正交映射（`plane-icon.js:20 shapeOf()` 的路子）。
4. **不用 `ctx.rect()`**。测试桩（`wx-stub.js:27`）和 `svg-ctx.js` 都没有这个方法 —— 用了会 `TypeError`。用 `moveTo/lineTo` 或 `draw.roundRectPath`。
5. **不用 `shadowBlur` / `filter` / `globalCompositeOperation` / `createConicGradient` / `setLineDash`**。投影用"偏移半透明块"。
6. **新 ctx 方法一律先特性探测**：`typeof ctx.xxx === 'function'`，缺了降级成纯色/平涂，**不能抛**。`test-layout.js:19` 的 Proxy 桩会把未探测的调用变 TypeError。
7. **扫掠段数 N=10 不要砍**。N=6 的段间台阶是 6/255（不是 11/255），省 4 次 fill —— 仍然不值，但知道正确数字再决定。
8. **1px 线一律取 `max(1, 比值)` 下限**。30px 屏上 0.028C = 0.84px 会被抗锯齿抹成灰雾。
9. **动效时间只来自 `fx.time()`**：不读 `Date.now()`，不用帧计数器，不在状态切换时复位。
10. **皮肤只能改"环境 + 身份色"**。红橙绿在 `SEMANTIC` 里，皮肤对象上根本没有这三个键 —— 不要为了"某套皮肤更好看"去动它。
11. **`js/shared/**` 不许 require `core/` 或 `widgets/`**。方向反了，小程序端和 `sync-shared.js` 一起崩。
12. **`tick` 里 `frame` 必须包 `try/catch` 且异常后仍重排 rAF**。一帧画错可以难看，永久黑屏不行。
