1项目背景与目标

1.1 项目背景

「炸飞机」是一款源自纸笔时代的经典双人对战游戏：玩家在 9×9 棋盘上布置自己的飞机，双方轮流报出坐标进行「轰炸」，先击毁对方全部飞机者获胜。规则直观、单局时长短、对抗性强，天然适合做成即点即玩的微信小程序。

传统纸笔玩法存在几处明显局限，数字化后可逐一解决：

纸笔玩法的局限数字化解法
必须面对面，无法远程约战在线房间 + 房间号/密码分享到微信，随时随地开局
手动画格、手动记落点，容易记错系统自动记录命中/未命中，可视化棋盘推演
双方口头判定，易起争议系统自动判定命中、击毁、未击中，杜绝争议
玩完即散，无沉淀无留存预留积分等级体系，构建长期留存

1.2 产品目标

核心目标
单局 3–5 分钟

支持好友实时对战与公开随机匹配，节奏轻快

体验目标
30 秒上手

新用户 30 秒内理解规则并完成首次布阵

社交目标
零成本拉新

房间号 + 密码分享到微信，好友一键加入

长期目标
可持续留存

以积分等级、多机型扩展构建成长线

1.3 本期（MVP）范围

本期做「核心对局闭环 + 轻社交」：玩家能建房/匹配 → 布置飞机 → 轮流轰炸 → 判定胜负 → 结算再来一局，并可微信分享邀战、发送局内快捷表情。积分等级、成就、观战等留到后续迭代，但底层数据结构须提前预留（见附录 A）。

范围边界本版不含：账号注册与登录体系（依赖微信授权临时身份）、积分等级、排行榜、成就系统、对局观战、弹幕、防作弊风控、付费内容。
本期新增：社交与邀请（微信分享邀战、最近对手快捷邀请、局内快捷表情）；道具系统仅做数据结构预留，功能于 V2 实现。

3核心玩法规则定义

3.1 棋盘

  • 尺寸：9 × 9 = 81 格，固定不变。
  • 坐标：横轴 1–9 记作「横」，纵轴 1–9 记作「竖」。
  • 报点格式：「横 X，竖 Y」。例如「横七竖八」= 第 7 列第 8 行（左上角为原点）。

3.2 飞机结构

每架飞机由 10 格组成，四个部件沿机体中轴排列：

  • 机头 — 1 格，被击中即整机击毁
  • 机翼 — 5 格，横向展开，中格与机头相连
  • 机身 — 1 格，位于机翼另一侧
  • 机尾 — 3 格，与机身相连
形状确认1（机头）+ 5（机翼）+ 1（机身）+ 3（机尾）= 10 格，已与需求方确认无误。

3.3 布阵规则

规则项定义
飞机数量最少 1 架，最多 3 架（本版固定上限 3，可配置）
飞机方向支持 4 向旋转（机头朝上/下/左/右），自由摆放
重叠约束任意两架飞机不得占用同一格（机头、机翼、机身、机尾全部格位均不可重叠）
出界约束飞机所有格位必须落在 9×9 棋盘范围内
摆放方式拖拽移动 + 点击旋转；支持「随机布阵」一键生成
可修改性仅在「布置阶段」可调整；点击「就绪」后本局锁定
布阵限时限时 60 秒（可配置）；超时未就绪则自动随机布阵并强制就绪

3.4 回合机制

本版采用严格交替：无论命中与否，开完一炮即换对方出手。

A 报坐标
系统判定
B 收到反馈
换 B 报坐标
循环至一方全灭
  • 先手：开局由系统随机决定，并以动效明确提示「你先开炮 / 对方先开炮」。
  • 重复报点：玩家重复报已炸过的坐标时，系统应拦截并提示「该坐标已轰炸过」。
  • 回合限时：每回合限时 30 秒（可配置）。超时则该回合自动跳过（不判负）；同一玩家连续超时 3 次判负。
  • 投降：对局中提供「投降」入口，二次确认后立即判负。

3.5 命中判定与反馈

命中部位系统反馈对方棋盘表现说明
机头击毁仅标记该机头格为击毁，不揭示飞机其余格位与朝向机头是唯一「击毁开关」，打中即整机报废
机翼 / 机身 / 机尾击中该格标记为受损飞机未损毁，仍可继续被炸
空白格未击中该格标记为已试未中用于排除范围、推演飞机位置
规则要点机头被击中 = 该飞机立即击毁，与其余 9 格是否已被击中无关。这是本游戏与普通翻格子玩法最大的差异，也是策略核心——玩家要推演的是「机头在哪」，而不是「打光所有格子」。
另：被击毁的飞机不揭示形状与朝向——在对方全部飞机被消灭之前，同一架飞机仍可能存在于不同方向，方向推理本身就是玩法的一部分。

3.6 胜负与结算

  • 胜利条件：率先击毁对方全部飞机（每架飞机构成 1 次击毁）的一方获胜。
  • 失败条件：己方全部飞机被击毁。
  • 平局：本版不设平局；理论上不存在同时全灭。
  • 对局结束后展示：胜负结果、双方剩余飞机、总出手次数、本局耗时，并提供「再来一局 / 返回大厅」。

5功能需求详述（EARS）

以下需求按 EARS 句式撰写，确保表述无歧义。类型标记： Ubiquitous 通用 Event 事件 Unwanted 异常 State 状态 Optional 可选

5.1 账号与入口

编号需求描述类型
ACC-01系统应始终以微信授权获取的临时身份标识玩家，在用户未主动跳转的情况下不弹出额外的注册/登录流程。Ubiquitous
ACC-02当用户首次进入小程序时，系统应展示规则引导页，并允许用户选择「跳过引导」。Event

ROOM-02当玩家点击「创建房间」时，系统应在 2 秒内生成房间号并进入「等待对手」状态。Event

ROOM-04当玩家选择「密码房」时，系统应生成一个 4 位数字密码，并生成可分享到微信的邀请卡片。Optional

编号需求描述类型
DEP-01系统应始终保证每名玩家在布阵阶段只能看到并操作自己的棋盘。Ubiquitous

5.4 对战模块

编号需求描述类型
BAT-01系统应始终保证同一时刻只有一方处于可行动状态，另一方处于等待状态。Ubiquitous

BAT-03当玩家提交一个坐标时，系统应即时判定该坐标对应的格位状态（空 / 机翼机身机尾 / 机头）。Event

6.2 对战界面：上下双层 + 焦点切换

对局主界面采用上下两个棋盘布局，解决「既要看自己挨了多少炸、又要记自己炸过哪儿」的认知负担：

区域显示内容作用
上半区 · 我方海域己方飞机完整形状 + 每格受损状态掌握自身存活情况，判断哪架飞机岌岌可危
下半区 · 敌方海域我方已轰炸点位（命中 / 击毁 / 未中）作为「战况地图」，推演对方飞机位置、锁定机头

焦点切换机制：默认「轮到谁行动、焦点就落在哪个棋盘」。玩家可手动点击某一棋盘将其放大为操作焦点，另一棋盘缩小为概览；行动权切换到对方时，焦点区域应同步切换并给出明确的高亮/动效反馈。

交互目标让玩家在一眼之间同时掌握「我还剩几格」与「对手的机头可能在哪」，从而做出下一步轰炸决策——这正是本游戏策略性的来源。

6.3 报点操作方式（「点选 + 发射」两步式）

为从源头杜绝「重复报点」，出招设计为两个明确步骤：

  1. 玩家在「敌方海域」棋盘上点选一个尚未攻击过的空格——已被轰炸过的格位置为灰化 / 禁用状态，无法被选中。
  2. 选中后该格高亮，玩家点击「发射」按钮确认出手。
  3. 系统即时判定并回显结果（击中 / 击毁 / 未击中），随后自动切换到对方回合。
设计意图界面层直接屏蔽已炸坐标，玩家物理上不可能误报；服务端仍保留二次校验（BAT-09）作为并发兜底。

布阵超时玩家未在限时内就绪自动随机布阵并强制就绪
对手中途退出一方主动关闭/退出判其负，另一方获胜并结算
房间超时无人加入创建后 5 分钟无人进入自动解散并提示房主
重复报点尝试点选已轰炸过的坐标界面层灰化不可选中；服务端二次校验拒绝
飞机数量为 0玩家未放飞机就点就绪拦截，提示「至少布置 1 架飞机」
并发操作冲突双方几乎同时提交以服务端接收顺序为准，确保状态唯一

9验收标准

  • 两名玩家可通过公开匹配或密码房成功进入同一房间并开始对局
  • 布阵阶段可自由摆放 1–3 架飞机，支持 4 向旋转，重叠/出界位置被正确拦截
  • 双方就绪后自动开局，先手方随机且提示明确
  • 报点后系统正确判定并反馈「击中 / 击毁 / 未击中」三种状态
  • 打中机头时，仅该机头格被标记为击毁，不揭示飞机其余格位
  • 上下双棋盘状态同步，且焦点可随行动方自动/手动切换
  • 一方全部飞机被击毁后，正确判定胜负并展示结算数据
  • 重复报点、超时、对手退出等异常场景均按规则正确处理
  • 断线后 60 秒内重连可恢复到原对局状态
  • 报点采用「点选未攻击格 + 点击发射」两步操作，已攻击格位不可选中
  • 击毁飞机后仅标记机头格，不揭示其形状与朝向
  • 布阵超时自动随机布阵；回合超时自动跳过，连续 3 次判负；投降二次确认后判负
  • 可生成微信邀请卡片，被邀请者点击直达房间；可一键再邀请最近对手
  • 飞机机型与道具均由配置驱动，新增类型无需改动核心逻辑

11后续迭代规划

本期虽不实现以下能力，但数据结构与界面须预留扩展位，避免 V2 重构。

11.1 积分与等级体系（V2）

  • 胜负积分：胜 +N，负 −M（基于对手段位差动态计算，参考 Elo）。
  • 段位：青铜 → 白银 → 黄金 → 铂金 → 钻石 → 王者，按积分区间划分。
  • 成就系统：首胜、连胜 5 局、一发击毁机头等。
  • 排行榜：好友榜 + 全服榜。

11.2 多机型扩展（V2）

  • 引入「飞机图鉴」：不同机型拥有不同形状、格数与稀有度（如侦察机 6 格、轰炸机 12 格）。
  • 房间配置支持选择「本局使用哪些机型」。
  • 要求：飞机形状数据驱动，而非写死代码（见附录 A）。

11.3 社交与邀请（本期同步交付）

  • 微信分享邀战：生成邀请卡片分享至好友 / 微信群，点击直达对应房间。
  • 最近对手：记录最近对局对象，支持一键再次邀请。
  • 局内快捷表情：轻量互动，不打断对局节奏。
  • 本期不做：对局观战、弹幕。

11.4 道具系统（V2 实现，本期预留数据结构）

为提升娱乐性与对局变数，规划在对局中引入道具玩法：

  • 超级导弹：使用一次可同时攻击 2 个坐标点。
  • 道具的获取方式（如击中 / 击毁飞机后掉落、对局随机补给）后续单独设计。
  • 硬性要求：道具同样采用数据驱动（见附录 A），新增道具无需改动核心逻辑。

附录 A · 数据结构预留设计

为了让「增加不同类型飞机」无需改代码，飞机形状应抽象为配置化的相对坐标。以下为标准机（10 格）的示意配置：

飞机模板（可扩展多机型）

字段类型说明
idstring机型唯一标识，如 standard
namestring机型名称，如「标准机」
cellCountnumber占用格数，本机型为 10
headIndexnumber机头在 cells 数组中的下标（决定击毁开关）
cellsarray相对坐标数组 [row, col]，机头为原点基准
raritystring稀有度，V1 固定为 common

标准机配置示例

{
  "id": "standard",
  "name": "标准机",
  "cellCount": 10,
  "headIndex": 0,
  "cells": [
    [0, 2],
    [1, 0], [1, 1], [1, 2], [1, 3], [1, 4],
    [2, 2],
    [3, 1], [3, 2], [3, 3]
  ]
}

道具模板（可扩展多道具）

字段类型说明
idstring道具唯一标识，如 super_missile
namestring道具名称，如「超级导弹」
descstring效果描述文案
effectTypestring效果类型，如 multi_shot（多发攻击）
paramsobject效果参数，如 { "targets": 2 }
raritystring稀有度

超级导弹配置示例

{
  "id": "super_missile",
  "name": "超级导弹",
  "desc": "使用一次可同时攻击 2 个坐标点",
  "effectType": "multi_shot",
  "params": { "targets": 2 },
  "rarity": "epic"
}
扩展性说明新增机型或道具只需追加一条配置记录，摆放校验、命中判定、棋盘渲染均可复用同一套逻辑——无需修改核心代码。
